# vision・UX・feature をつなぐ機能見直しとヒアリング

**状態:** 生きたリファレンス。2026-10-16 作成。
**対象:** プロダクトの開発方針を、オーナー・学習者・教員と確認するための進行表。
アプリ内のヒアリング機能の仕様ではない。

[ビジョン](vision.md) → [サービスデザイン](service_design.md) → **本書の利用場面と質問** →
[機能仕様の索引](README.md) → [利用者マニュアル](manual/README.md) の順にたどる。
思想の正本は vision、個別仕様の正本は各設計書（追補を含む）。本書は判断への入口であり、
機能名・状態・優先順位の独立した正本を増やさない。

## 1. ヒアリングの進め方

最初の問いは **「最近、論文を読んだり教材を用意したりする中で、どこから先へ進めなくなりましたか」**。
具体的な一場面を選び、次の順に一問ずつ聞く。G番号やレイヤー名を利用者に覚えてもらう必要はない。
既に答えが出た項目は聞き直さず、最後に一つの流れとして読み返す。

| 順 | 聞くこと | 残すもの | 次へ渡すもの |
|---|---|---|---|
| 1. 場面 | 誰が、何を使って、何をしようとしていましたか。実際の一例を教えてください | 役割・教材・開始状態・詰まった箇所。観察と想像を区別 | §2 の対象場面 |
| 2. vision | その場面の後、あなた自身が何を判断・説明できれば役立ちますか | 望む変化を本人の言葉で一文。関連する vision の節 | 体験の目的 |
| 3. UX | 今はどう進めていますか。どこで迷い、止まり、翌日どう再開しますか | 入口 → 行為 → 根拠の確認 → 残るもの → 再訪の操作列 | 機能間の不足 |
| 4. feature | 既存のこの操作で足りますか。足りないのは入口・情報・操作・保存・再開のどれですか | 既存で足りる／接続を直す／新設が必要／まだ不明。§2 の仕様リンク | 最小の変更候補 |
| 5. 境界 | 残さず終える、取り消す、共有しない、AI が使えない場合はどうあるべきですか | 見え方・保存先・拒否・空状態・失敗時の期待 | 守る条件と例外 |
| 6. 確認 | この流れができれば目的を満たしますか。まず一つ直すならどこですか | 合意した範囲・未回答・受入場面・見送ること | 設計・検証への入力 |

回答のない箇所は「未回答」、観察していない挙動は「未検証」とする。
提案を本人の要望として書かない。実装があること、テストが通ること、体験が成立することは別々に扱う。

## 2. 場面別の機能見直し

2026-10-16 のローカル実装・設計書と、既存の
[第23周の記録](architecture/persona_enactment_testing_design.md) §20.6〜20.10 を照合した。
第23周の所見は当時の観察であり、本書作成時にブラウザで再演した結果ではない。
全機能の監査ではなく、vision と UX をつなぐ主要な境界の見直しである。

| 場面 | vision → 求める UX | 使う機能・仕様 | 見直しの見解／ヒアリングで確かめること |
|---|---|---|---|
| J1 論文を読み始め、分からない所へ降りる | §2.1・§3.1 → 自分の問いを置き、必要な根拠へ戻れる（G1・G2） | [論文と議論する](features/discussion_mode_design.md)・[理解サイクル](features/understanding_cycle_design.md)・[構造の降下路](features/structure_descent_design.md) | **既存の入口をつなぐ。** 予想・説明・原文のどこで止まったかを聞く。精読は議論の開幕に予想を挟むが教材本文は隠さない。「答えを見る前」が教材全体を指すなら別の要件 |
| J2 中断して翌日戻る | §3.4・§3.7 → 本人の言葉から、督促なく再開できる（G2・G3） | [帰還の扉](features/return_door_design.md)・理解サイクルの持ち越し | **優先して循環を通す。** 書き置き・持ち越しの保存と再表示は実装あり。第23周では逐語の再表示を確認した一方、答えた後も扉が変わらない所見がある。問い・予想・書き置きのどれに戻りたいか、本人がいつ置き換えるかを聞く |
| J3 考えを言い直し、取り消す | §3.7・§5.2 → 訂正でき、何が残るか分かる（G3・G6） | [痕跡の主権台帳](features/trace_registry_sovereignty_ledger_design.md)・[わたしの地図](features/personal_knowledge_network_design.md) | **操作の違いを明確にする。** 会話の書き直し・地図からの除外・候補の見送りは別経路。見送った候補を戻す操作は無い。「隠す」「消す」「戻す」のどれが必要かを聞き、単一の削除機能にまとめない |
| J4 記録を読み返し、扱われ方を確かめる | §5.2・§5.4 → 誰に見えるか・何が残るかを理解して選べる（G6） | 主権台帳の「わたしの記録」・[可視性6軸](features/disclosure_axes_design.md)・[アカウントライフサイクル](features/account_lifecycle_management_design.md) | **説明と実際の経路を揃える。** 一覧・持ち出し・外部 AI の告知は実装あり。告知は同意ではなく、会話全体の書き出しも無い。答えられなかった質問の教員への開示は §3 D1 で判断する |
| J5 教員が教材を確かめ、公開する | §4・§5.1 → 根拠と代替を見て、未確認を区別して公開できる（G5・G7） | [リリース前の確認](features/release_review_flow_design.md)・[確定文脈](features/decision_context_design.md)・[版管理](features/shared_versioning_design.md) | **確認の手数より判断の成立を見る。** 確認せず進む・閲覧のみ・別コースで確認済みの各経路を聞く。配置の確認は全生成物のレビューではない。第23周の閲覧のみ経路は砂場で再演できておらず、API テストと通し検証を区別する |
| J6 論文から関連研究へ進む | §2.1・§2.4 → 根拠のある近傍をたどり、自分で次を選ぶ（G1・G5） | [コーパス回遊](features/corpus_roaming_design.md)・[ライブラリ](features/image_pipeline_knowledge_library_design.md)・[ディスカバリー](features/paper_discovery_design.md)・[論文レーダー](features/paper_radar_design.md) | **学習者の回遊と教員の取り込みを区別して接続する。** 既存コーパス内の移動と外部論文の検索・解析は別。候補を選ぶ根拠、解析前後で分かること、次の起点への引き継ぎを聞く。進行中のローカル変更を含むため、この循環を検証済みとはしない |
| J7 自分で確かめ、後で書く | §2.2・§3.7・§5.4 → 再導出・再現・比較の条件と結果を自分の記録に残す（G4・G3） | [検証シミュレーション](features/simulation_bridge_design.md)・[再構成ループ](features/reconstruction_loop_design.md)・[D層](features/doubt_layer_issues.md)・[SL層](features/stakes_ledger_design.md)・[未実装の構想](vision.md) §9 | **既存の再構成と検証シミュレーションから始める。** 成功した run の `verification_attempt` は本人の記録へ保存される。一般の手計算・外部実測の記録や TeX/BibTeX の来歴書き出しまで実装したものではない。何を試し何を残したいかを聞き、不足分を定める。共有は本人の操作、台帳の確定は教員の判断 |

## 3. 先に決める判断点

ここは**質問と推奨**であり、合意済みの仕様ではない。第23周 §20.9 の裁定待ち事項も含む。

| ID | 質問 | 現行・選択肢と推奨 | 影響する範囲 |
|---|---|---|---|
| D1 | 教材から答えられなかった質問は、誰にどこまで渡すべきか | 現行は表示名と本文を担当教員へ開示し、会話削除でも残る。現行維持／匿名集約／本人が選んだ質問のみ共有を比較する。**本人の選択を経る経路を優先して検討**するが、既存の §20.9 の推奨とは異なるため未決と明示する | vision §5.2、教員の不足教材の把握、開示宣言・撤回・既存記録の扱い。[IK-0658](issue_knowledge/entries/IK-0658-withdrawn-question-stays-in-unanswered-log.md) |
| D2 | 「予想を置いてから読む」は議論だけか、教材本文にも及ぶか | 現行の議論内の opt-in を維持することを推奨。本文を伏せるなら教員が教材ごとに選ぶ別要件として設計し、通常の読書を妨げない | J1、教材表示、理解サイクル。§20.9 の裁定待ち |
| D3 | 中断から戻るとき、何を選び直したいか | 問い・予想・書き置きを区別し、本人が持ち越しを置き換える流れを先に確かめる。AI が解決済みを決めたり督促したりしない | J2・J3、帰還の扉・意図・再訪。[IK-0668](issue_knowledge/entries/IK-0668-return-door-unchanged-after-carryover-answered.md) |
| D4 | 見送った候補を後から戻す必要があるか | 復帰経路の検討を推奨。ただし「戻す」際の候補状態、再確認、地図・集約への反映範囲を先に決める。現行の状態保持を復帰機能の実装済み扱いにしない | J3・J4、主権台帳・帰属候補。[IK-0660](issue_knowledge/entries/IK-0660-dismissed-candidate-cannot-be-restored.md)、§20.9 の裁定待ち |

## 4. 進める順序と受入場面

1. **説明の整合を先に直す。** サービスデザインの「本人のみ可視」「削除しない」「確定」の
   射程を原則と現行仕様に合わせる（今回修正）。§3 の回答は未取得。
2. **既存の循環を優先する。** J1 → J2 → J3 → J4 を一つの教材で通す。
   予想を置く → 出典と比較する → 本人の言葉で残す → 翌日戻る → 書き直す → 残った記録を確かめる。
   機能追加の前に、入口・保存成功・再訪・取り消しの境界を確認する。
3. **教員の判断から学習者の表示まで通す。** J5 は所有者／閲覧のみ、未確認あり／ゼロ、
   一部却下／あとで、別コースでの確認済みを用意する。提示集合と操作対象と監査記録、
   学習者に届く状態が一致するかを見る。J6 は解析前の候補と解析後の根拠の違いを確認する。
4. **不足する行為だけを新設する。** J7 の試行記録の拡張や書く出口は、その場面の回答が得られてから
   専用設計へ進める。新しい大画面、全機能を束ねた万能チャット、個人スコア、新しい通知は
   本見直しからは提案しない。

正常系だけでなく、何も残さない・候補ゼロ・保存失敗・AI 不可・権限なしも確認する。
確認方法は [ペルソナ通し検証](architecture/persona_enactment_testing_design.md) に接続する。
過去に到達できなかった場面やハーネス由来の所見を、製品の成功／失敗に数えない。

## 5. 回答を設計へ渡す記録様式

一場面につき次を記録し、話し手へ読み返す。短い答えでも、機能名から仕様を補完しない。

```text
日付／話し手の役割／場面 J番号:
実際に起きたこと（本人の言葉）:
望む変化／vision の参照節:
入口 → 行為 → 根拠 → 残るもの → 再訪:
既存機能・仕様リンク／不足する境界:
見える相手・保存・撤回・失敗時の期待:
観察事実／仮説／提案／本人の回答:
判断点 D番号／決定・未回答・保留／理由:
採用する変更／見送る変更:
受入場面・検証方法・未検証範囲:
更新する設計書・サービスデザイン・マニュアル:
```

今回の整理は回答を得た記録ではない。オーナーの判断を要する項目は未回答のまま残す。
判断したらこの様式から個別設計書へ移し、本書はリンクと次に聞く質問を更新する。

## 6. 文書整合の確認と更新

今回確認した範囲は検証シミュレーション §14 とその実装、vision §3〜§6・§8〜§9、サービスデザイン、§2 の仕様と実装入口、
第23周の結果と裁定待ち事項。サービスデザインには次の修正を行った。

- vision §8・§9 と機能一覧に検証シミュレーションの実装済み範囲を反映。未実装の記述から重複新設を誘発しないよう補正。
- 9月改訂の「可逆な循環」「三領域の分離」「再構成可能な確定手続」を要約へ反映。
- 環境の課題、体験の設計意図、現行実装、通し検証を区別。
- 精読の射程、名前付き質問の開示、取り消しと物理削除の違いを現物に合わせた。
- 「数値を見せない」を用途・粒度の統治へ、機械検査の保証を参照・網羅等の範囲へ補正。

**更新の契機:** 原則を改訂したとき、機能間の受け渡しを変えたとき、開示・保持・撤回を変えたとき。
変更担当が [開発チェックリスト](development_checklist.md) に沿い、本書の場面から
サービスデザイン → 機能仕様 → マニュアルを往復する。過去の調査結果は書き換えず、現行の仕様へリンクする。
既存の [文書ガードレール](../backend/tests/test_docs_registry_guardrails.py) はリンク実在等を検査する。
意味の整合やヒアリングの使いやすさは、読み合わせと次回の実際のヒアリングで確認する。
