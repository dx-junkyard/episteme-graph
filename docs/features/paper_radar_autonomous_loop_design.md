## 1. 目的と不変条項

論文レーダーの UX を、画面を眺めるだけでなく**実物の連鎖**で確かめる。処理済みの教材を起点にレーダーで arXiv を探し、
分野のペルソナが研究対象として関心を持てる候補だけを取り込み、パイプラインを通した後の構造（位置づけ・理論モジュール・
論文層・参照健全性）と AI 比較で近さを読み、次の起点へ連鎖する — を止めるまで回す。関心が持てない周は「画面に何が
足りないか」を仮説にして製品を直し、同じ起点で再検索して網の変化を見る。

既存の不変条項 **PR1〜PR8**（[論文レーダー](paper_radar_design.md)）と **PD1〜PD8**（[論文ディスカバリー層](paper_discovery_design.md)）を
すべて継承する。周回に固有の追加は次の 4 つ。

| ID | 条項 | 守り方 |
|---|---|---|
| AL1 | **取り込みの弁は教員の明示操作のまま**。周回はハーネスが教員の明示操作を代行する立場で、製品に自動クロール・worker・cron からの取り込み経路を足さない（PD1） | 取り込むのは審判の decision に `ingest` が書かれたときだけ。ハーネスは製品の HTTP API だけを叩き、製品コードを import しない（PE2 と同じ立場） |
| AL2 | **arXiv への到達は 1 周あたり最大 2 回**（レーダー検索 1 + 取得 1。P-0007・paper_radar_design §14 の予算） | seed のメタデータと比較の要旨は写し（`paper_discovery_arxiv_metadata_cache`）で 0 回。呼び出しの間隔は 4 秒。429 の冷却中は検索せず待つ |
| AL3 | **判定の主語は分野のペルソナ**で、近さの数値ではない。審判の記録にも数値（cosine・confidence・件数）を材料として書かない（PR2 / PD4 / PE10） | 審判の規律（`uxsim/runs/radar_loop/` の JUDGE_INSTRUCTIONS（git 管理外））。判定は「持てる / 条件付き / 持てない」と本人の言葉 |
| AL4 | **LLM は bridge で肩代わりし、embedding は本物**。製品の chat.completions は proxy → mailbox → 頭脳（Opus の子エージェント）が応え、`/v1/embeddings` は proxy が本物の OpenAI へ素通しする（P-0011） | 帯分け・着地・関連度は本物のベクトルで動く。頭脳は要求の messages だけから答え、外部 API を呼ばない |

蓄積先は依頼で指定された開発スタックの教員アカウントの教材で、周回で取り込んだ論文はその教材一覧に残る（P-0023）。

## 2. 方式 — 浅い段・深い段・審判の handshake

driver v2（`uxsim/sandbox/radar_loop.py`）は 1 周を 2 段に分け、各段の終わりに**審判のファイルを待つ**。

| 段 | driver がすること | 書くもの | 待つもの |
|---|---|---|---|
| 浅い段（scan） | `GET radar/seed` →（出所が推定かつ題名一致なら画面と同じ 1 回の `POST radar/provenance`）→ `POST radar/search` → 未取り込み・未試行の候補の上位 K 件を `POST radar/compare`（LLM 1 コール） | `scan-NN.json`（seed・検索条件・候補・比較・HTTP 呼び出しの記録） | `scan-NN.decision.json` |
| 深い段（deep） | 審判が選んだ 1 本を `POST ingest`（TeX 既定）→ `tasks/{id}` を完了まで待つ → 類似性の材料（compare・landscape placements・theory-modules + related・reference-health・paper-layer・新しい seed）を集める | `deep-NN.json` | `deep-NN.decision.json` |

decision の形:

```text
scan: {"ingest": "<arxiv_id>" | null, "next": {"seed": "chain"|"stay"|"<document_ref>", "distance": "near"|"mid"|"far"}, "note": "..."}
deep: {"next": {"seed": "chain"|"stay"|"<document_ref>", "distance": "..."}, "note": "..."}
```

- **連鎖**: `seed: "chain"` は取り込んだ論文を次の起点にする / `stay` は同じ起点で距離だけ変える / document_ref は別の教材へ移る。
- **台帳**: `ledger.json` の `tried` が試した arXiv ID と結果（`ingesting` 等）を持ち、同じ候補を二度試さない。
- **STOP**: 出力ディレクトリに `STOP` ファイルを置くと、次の arXiv 呼び出しの前で止まる。decision 待ちの間も 15 秒ごとに見る。
- **attach**: 既に走っている解析（document_id / arxiv_id / task_id）を深い段として引き取るサブコマンド（driver の再起動で
  走行中の取り込みを失わないため）。
- **審判**は別の子エージェントで、`scan-NN.json` を全部読み、ペルソナ（宇宙物理パックの教員・学生から主題に近い 2〜3 人）の目で
  judge-scan-NN（Markdown。起点と候補の関係 3 行 / ペルソナごとの判定 / 画面で見えた材料と判定に使った材料 / 改善の仮説 ≤5・
  課題ナレッジの型付き / 次の周）を書き、decision を置く。

## 3. なぜ「取り込んでから確かめる」ではなく「審判を先に挟む」のか

依頼の素朴な形は「近い候補を順に取り込み、パイプラインを通してから類似性を確かめる」だった。v1 の driver はそうしたが、
1 周目で次が分かった。

- 頭脳が製品 LLM の 1 コールを 1 応答で肩代わりする運転では、**TeX 論文 1 本の解析に 10 時間を超える**（役割判定が
  本文ブロック 1 件 = 1 コール — IK-0699。さらに TeX の環境残骸・前付け・表の行が 1 件ずつブロックになって母集合を
  膨らませていた — IK-0696）。
- 1 周目の「近い」候補は起点の主題と無関係なカテゴリの新着だった（§5）。それを取り込んで 10 時間待っても、得られるのは
  「関係が無い」という知見で、それは要旨と比較を読めば数分で分かる。

そこで v2 は**安い段（検索・比較 = arXiv 1 回 + LLM 1 コール）で審判の判定を先に取り、関心が持てる候補だけを高い段
（取り込み・解析）へ進める**。これは製品の不変条項とも同じ形をしている — 取り込みの弁は人（ここでは人を代行する審判）の
明示判断にある（PD1 / AL1）。同時に、浅い段で関心が持てない理由がそのまま「画面に欠けている要素」の仮説になり、
解析を待たずに是正の波を回せる。

周回中だけ、overlay（§4）で役割判定・主張採否・式の意味の段階上限（節単位の層化サンプリング）を置ける。母集合の被覆は
`stage_outputs` の coverage に正直に残り、本番の既定（上限なし・J-3）は変えない。

## 4. 運転の手順

1. **開発スタックで回す**（`docker compose -f docker-compose.yml -f docker-compose.local.yml`）。蓄積先が開発スタックの
   教員アカウントの教材だから。パスワードは環境変数 `RADAR_LOOP_PASSWORD`（ファイルに書かない）。
2. **bridge overlay を api-server にだけ重ねる**（`uxsim/sandbox/docker-compose.bridge.yml`）:
   `docker compose -f docker-compose.yml -f docker-compose.local.yml -f uxsim/sandbox/docker-compose.bridge.yml up -d --no-deps api-server`。
   overlay は `OPENAI_BASE_URL` を proxy（`uxsim/sandbox/claude_proxy.py --port 8090`）へ向け、`EPISTEME_DEFAULT_CARTRIDGE_ID`
   を空にし（分野は入口で選ぶ = F9。開発機の `.env` は既定分野を持つ）、周回用の段階上限を env で渡せるようにする。
   外すときは同じ 3 ファイルから overlay を抜いて `up -d --no-deps api-server`。
3. **頭脳を起こす**: 製品頭脳は Opus の子エージェントを複数（`seq % N == r` で担当を分け、相手の seq に触らない）。規律は
   `uxsim/runs/radar_loop/` の BRAIN_INSTRUCTIONS（git 管理外。要求の messages だけから答える・JSON Schema は厳密に・応答ファイルは自分専用の名前・
   1 要求 1 行の所見メモ BRAIN_NOTES_<レーン名>・40 件で交代）。補助 CLI は `uxsim/sandbox/brain.py`（pending / show / answer）。
4. **driver を起こす**: `backend/.venv/bin/python -u -m uxsim.sandbox.radar_loop run --seed <document_id> --distance near
   --cartridge-id "" --compare-top 5 --gap 600 --out uxsim/runs/radar_loop`（429 の後は `start_driver.sh` が 15 分待ってから再開する）。
5. **上限で落ちたときの復帰**: 頭脳が利用上限で落ちると mailbox に未応答が溜まり、製品側は待ち続ける。復帰は新しい頭脳を
   同じ担当分けで起こし直し（所見メモは新しいレーン名で）、放棄する要求には `{"error": …}` を置く。driver は decision を待つ間は
   何もしないので、審判が落ちたら審判を起こし直せばよい。driver 自体が落ちたら `attach` で走行中の解析を引き取る。
6. **製品への反映は解析の切れ目にまとめる**: 走行中の解析がある間は api-server を再作成・再起動しない（IK-0601・改善サイクル §2.5）。
   再起動のたびに走行中の解析が止まり、resume が役割判定のステージを最初からやり直す（IK-0710 — 同じブロックへの LLM 呼び出しが
   繰り返される）。是正は波にまとめ、解析が終わってから 1 回で反映する。**api-server を再作成したら proxy も再起動する**（§10）。
7. **再作成すると `docker cp` で入れたファイルは消える**: `compose up` が api-server を再作成すると、コンテナへ `docker cp` で
   入れた修正は失われる。反映はイメージの再ビルドか、再作成の後にもう一度入れ直す。どちらで入れたかを周回の記録に残す。
8. **止める**: `uxsim/runs/radar_loop/STOP` を置く。頭脳も STOP を見て終了する。

## 5. 実測の記録

記録の実体は `uxsim/runs/radar_loop/`（git 管理外）。起点は 2 本の解析済み教材（大規模構造の尖度整合関係で重力理論を検証する
宇宙論の理論論文 / b→c セミレプトニック崩壊の和則の素粒子現象論の論文）。どちらも承認済みの理論部品が無い状態だった。

| 周 | 何が起きたか | 審判の判定 |
|---|---|---|
| scan-01（near・是正前） | キーフレーズ候補が空で、near のクエリが起点の 4 カテゴリの OR だけに縮退。返ったのは 4 カテゴリの**新着**で、主題（大規模構造・修正重力）を扱う候補は無かった。分野の地図が無く、着地・重なり・新しい面も全候補で空で、空である理由が画面に出なかった。AI 比較の「共通点」は一般論で埋まった | 3 人とも持てない。取り込まない。別の起点で再現するかを確かめる |
| scan-01b（手入力の参照） | 同じ起点に教員が手でキーフレーズ 4 語を足した near を 1 回だけ比べた。候補のほとんどが主題の論文になった — 縮退していない near がどんな網を張るかの参照 | （参照のみ） |
| scan-02（別の起点・near） | 素粒子の起点でも同じ縮退が再現（原因は起点ではなく「承認済み部品が無い」共通条件）。起点の題名がファイル名のままで、題名一致による出所の自動記帳が原理的に起きないことも見えた | 宇宙物理パックにこの起点の主体となるペルソナは立たない（と正直に記録）。取り込まない |
| scan-03（第 1 波の是正直後） | キーフレーズ供給の初版が主張の概念名から「予測値の範囲を述べた文」を拾い、それが `all:"…"` に入って該当ゼロ（`no_new_candidate`） | — |
| scan-04 | arXiv から 429（アクセス制限）。driver は検索をやめ、15 分待って再開した（paper_radar_design §14 の冷却） | — |
| scan-05（第 1〜2 波の是正後・near） | キーフレーズが題名と中心命題から供給され出所付きで並び、カテゴリは主カテゴリだけが既定で有効。候補はすべて宇宙論になり、高次統計・摂動論に直接触れる候補が現れた。縮退の理由は事実文になり、AI 比較は関係の種類（同じ対象 / 隣り合う話題 / 目立った共通点なし）に分かれた。一方で起点の核心語と重力側の語はどの候補にも当たらず、帯は全件「近い」で判断材料にならなかった | 大規模構造理論の教員と摂動論の学生が「持てる」。**周回で初めて取り込みの判定**（起点の尖度 = 4 点統計に正面から対応するトライスペクトルの full-shape 解析）。次は取り込んだ論文を起点に連鎖（chain・near） |

scan-05 の後、選んだ論文の取り込みと解析は走り出したが、起票時点では深い段の記録（`deep-NN.json`）と審判はまだ無かった

## 10. 運転の根 2 つ — 打ち切りと proxy の滞留

深い段の材料が出る前に、取り込んだ論文の解析で中心命題の再構成・DSL 接続・部品の組み立てが**決定論フォールバック**に落ち続けた。
根は 2 つで、1 つ目を直しても症状が消えなかったことが 2 つ目の切り分けになった。

| 根 | 何が起きたか | 是正 | IK |
|---|---|---|---|
| A層の打ち切り | agent の LLM 呼び出しの打ち切り（既定 300 秒 / 壁時計 330 秒）を頭脳の応答（1 応答に数分）が超え、フォールバックで出来た部品・空の中心命題のまま run は completed になり、教材は「解析済み」に見えた | 運転側: overlay に `RADAR_LOOP_AGENT_LLM_TIMEOUT_SECONDS` / `RADAR_LOOP_AGENT_LLM_WALL_TIMEOUT_SECONDS` を足し、周回中だけ延ばした（1500 / 1800 秒。本番の既定は不変）。製品側の「フォールバックで出来た成果を教材行・グラフレビューに示す」は open | IK-0715（open） |
| proxy のスレッドプール滞留 | 打ち切りを延ばしてもフォールバックが続いた。製品の log の送出時刻と mailbox の受付時刻が十数分ずれていた — proxy が要求ごとに応答待ちを既定スレッドプールに載せ、api-server の再作成で去った呼び出し元の待機がプールを埋め、新しい要求が proxy の中で待たされた | proxy の待機をスレッドを使わない非同期ポーリングにし、呼び出し元の切断を検知したら応答に `client_disconnected` の error を置く（頭脳の無駄も止める）。proxy の再起動時は未応答の要求に放棄の印を置く（`uxsim/sandbox/claude_proxy.py` の `_ask_async`） | IK-0726（resolved） |

是正後、トライスペクトルの論文は中心命題の再構成のステージから再開し（resume はステージの頭から — IK-0710）、本物の応答で
最後まで通った（フォールバックなし）。**運転の規律**: api-server を再作成したら proxy も再起動する（去った呼び出し元の待機を残さない）。
打ち切りの延長は overlay の env だけで渡し、製品の既定値は変えない。

## 13. 頭脳の利用上限による全滅と復帰

この日、製品頭脳（Opus の子エージェント）が利用上限で**3 回全滅**した。全滅すると mailbox に未応答が溜まり、製品側は待ち続ける
（打ち切りに達したものはフォールバックへ落ちる — §10）。復帰は §4 の 5 の手順を次のように具体化した。

1. 頭脳を**3 体**で起こし直す（`seq % 3 == r` で担当を分け、相手の seq に触らない。所見メモは新しいレーン名で — `BRAIN_NOTES_<レーン名>`）。
2. 上限の前に出された要求（呼び出し元がすでに打ち切った・api-server の再作成で去った）は**応えずに放棄**する（応答に error を置く）。
   古い要求に応えても、受け手がいないか、フォールバックの後に届いて使われない。
3. 解析は**ステージの頭から再開**する（IK-0710 — ステージ内の再開単位が無い）。全滅の前に応えた分も、そのステージでは呼び直される。
   再開の前に、どのステージがフォールバックで「成功」したかを stage_outputs の縮退の記録で確かめ、本物の応答で通し直す。

審判は decision を待つ間しか動かないため、全滅しても審判を起こし直すだけで driver の状態は失われなかった。
