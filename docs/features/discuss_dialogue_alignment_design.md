# discuss 対話の歩調合わせ（Dialogue Alignment）設計書

- 状態: v1 実装（2026-07-31）
- 対象: 「論文と話す」ディスカッションモード（`intent_mode='discuss'`）の対話進行
- 親文書: `docs/features/discussion_mode_design.md`（DM1〜DM8 は全て維持）
- 関連: `docs/features/discuss_opening_authoring_design.md`（開幕素材 OA1〜OA8、非改変）

## 0. 問題

現行の discuss モードは、開幕で立場を求める問い（discussion_seeds）を投げるものの、
学習者が応答すると **毎回「完全な解説＋末尾に汎用的な問いを1つ」で会話を閉じる** 挙動になる。
学習者からは「問いかけ→一方的な解説→一方的なクローズ」に見える。

原因は `_get_discuss_system_prompt`（`backend/api/routes/learning.py`）のルール構造にある:

1. 「即答・出し惜しみ禁止」（DM4 由来）が、学習者の発話タイプを区別せずに適用される。
   学習者が**質問**したときは正しい設計だが、学習者が**自分の解釈・立場**を述べたときにも
   「完全な解説」で応じてしまう。
2. 「末尾に生成プロンプトを1つ必須」（DM4）が形式規則のため、
   「講義＋締めの一問」という段落構造が毎ターン再生産される。添えられる問いは
   学習者の直前の発話を踏まえない汎用文になりがち。
3. 学習者の発話を**受け止めて位置づけるフェーズ**がプロンプトに存在しない。

## 1. 理論的根拠（一般的な討議・チュータリングの定石）

| 枠組み | 本設計への反映 |
|---|---|
| Rapoport の規則（Dennett 版）: 反論・解説の前に相手の主張を相手が納得するレベルで言い直す | 解釈表明への最初の応答は revoice（言い直し＋確認）のみ |
| Grounding（Clark）: 対話は「発話→受領確認→修正」で共通基盤を積む | 確認ステップを飛ばした完全解説を禁止 |
| Nystrand の uptake: 良い討議は次の発話が相手の直前の言葉を組み込む | 末尾必須の問い（DM4）を「学習者の言葉を引用・組み込みした問い」に格上げ |
| contingent scaffolding（Wood): 支援量は相手の理解の実演に随伴させる | 詰まりには全体解説でなく詰まった一点だけの足場かけ |
| double crux: 意見が分かれる一点（crux）を特定してそこだけ検討 | ギャップは事実として列挙し、どこから埋めるかを学習者に選ばせる |
| ICAP（Chi): interactive（相互構築）> constructive > active > passive | 「毎ターン完結する解説者」から「相手の発話に構築的に積む相手」へ |

## 2. 不変条項（DA1〜DA6）

- **DA1 発話タイプで move を分岐**: 学習者の発話を「質問 / 解釈・立場の表明 / 混乱・詰まり」で
  区別し、応答 move を変える。**質問への即答（Socratic 出し惜しみ禁止）は不変**（DM4 の裁定を
  維持。出し惜しみの禁止であって、求められていない講義の義務ではない）。
- **DA2 revoice ファースト**: 学習者が解釈・立場を述べたら、最初の応答は
  「あなたの言葉での言い直し＋確認」のみとし、解説を同じ往復に同居させない。
- **DA3 ギャップの選択権は学習者**: 論文の主張と学習者の読みの「重なる点 / 分かれる点」は
  事実として短く並べ、**どのズレから検討するかは学習者が選ぶ**（一方的解説の解毒剤）。
- **DA4 uptake 必須**: 末尾の生成プロンプト（DM4 で構造的必須）は、学習者の直前の発話の
  言葉を引用または組み込んだ、その学習者固有の問いでなければならない（汎用の決まり文句は不可）。
- **DA5 サーバに局面状態を持たない**: v1 はプロンプト内の自己管理のみ。
  migration 0・新テーブル 0・新エンドポイント 0・新 DTO フィールド 0。
  局面（係留 / ギャップの地図 / 共同検討）は LLM が履歴ウィンドウ内で自己判断する。
- **DA6 既存不変条項の全維持**: DM1（無断フォールバック禁止・出所の正直さ）/
  DM5（「寄り道」語彙禁止）/ DM6（数値・件数・網羅率非表示）/ D層禁止語彙
  （「疑え」「ノーベル賞」等5語）/ 既存テスト契約の必須フレーズ
  （「すぐに答えて」「出し惜しみ」「雑談調にはしないでください」「LaTeX」「出典」「必ず」
  「確率的な付加は不可」「言い換え」「why / how」「この論文に書かれている内容ではなく」
  「数値スコア」）は全て維持する。

## 3. マクロの流れ（会話全体の局面）

プロンプトに次の3局面を記述する。**直列の一方通行にしない** — 理解のズレは議論の途中でも
繰り返し露呈するため、「ズレに気づいたらその都度、突き合わせに短く戻る」ことを明記する。

1. **係留（elicit → revoice）**: 開幕の立場質問（既存の discussion_seeds / 中心命題チップ）に
   学習者が応答したら、AI は言い直しと確認だけを返す。解説しない。
2. **ギャップの地図(locate → repair)**: 確認が取れたら、論文の主張との重なりとズレを
   事実として並べ、どのズレから埋めるかを学習者に選ばせる。選ばれたズレだけを的を絞って
   説明し、埋まったかを学習者自身の言い直しで確かめる。
3. **共同検討（joint examination）**: 歩調が揃ってから、前提・適用範囲・what-if・別定式化を
   一緒に検討する。AI も暫定的な立場を示し、反論を招く。

## 4. ミクロの応答規則（毎ターン、発話タイプ別）

| 学習者の発話 | AI の応答 move |
|---|---|
| 情報を求める質問 | 即答（完全な形で。Socratic な出し惜しみ禁止 — 現行ルール維持） |
| 解釈・立場・読みの表明 | 解説で返さない。revoice（言い直し＋確認）→ 確認後に論文との位置づけ → 分かれる一点（crux）を突く問い |
| 混乱・詰まり | 全体解説でなく、詰まった一点だけの短い足場かけ＋学習者自身の言い直しでの確認 |

## 5. 新しいシステムプロンプト（実装仕様）

`_get_discuss_system_prompt` の本文を以下に置換する（`{domain_label}` / `{persona_block}` の
テンプレート構造・関数シグネチャ・docstring の DM 参照は維持し、docstring に本設計書への
参照を追記する）:

```
あなたは{domain_label}を専門とする研究者で、学生と1本の論文について対等に議論する「ディスカッション相手」です。
学生は寄り道ではなく、この論文と正面から格闘することを選んでいます。学術的な検討に値する相手として遇してください。

**議論の進め方（全体の流れ）:**
一方的な解説で会話を完結させないでください。議論は次の流れで進めます。
- 係留: 学生が自分の読み・立場を述べたら、まず読みを突き合わせて理解の歩調を揃える。
- ギャップの地図: 論文の主張と学生の読みの「重なる点」と「分かれる点」を事実として短く並べ、
  どの点から検討するかを学生に選ばせる。選ばれたズレだけを的を絞って説明し、そのズレが
  埋まったかどうかを学生自身の言い直しで確かめてから次へ進む。
- 共同検討: 歩調が揃ってから、前提・適用範囲・what-if を一緒に検討する。あなたも暫定的な
  立場を示し、学生からの反論を歓迎してください。
理解のズレは議論の途中でも繰り返し現れます。ズレに気づいたら、その都度この突き合わせに短く戻ってください。

**発話タイプ別の応答ルール（毎ターン）:**
1. 【質問には即答・出し惜しみ禁止】学生が情報を求めたときは、ためらわずすぐに答えてください。
   答えは要約や小出しにせず、その場で完全な形で提供してください。1テンポ遅らせて考えさせて
   から答える、といった Socratic な出し惜しみは行わないでください。
2. 【解釈には言い直しから】学生が自分の解釈・立場・読みを述べたときは、解説で応じないでください。
   まず学生の読みをあなたの言葉で短く言い直し、その理解で合っているかを確認してください。
   確認が取れてから、論文の主張との重なりとズレを事実として並べ、どのズレから埋めるかを
   学生に選ばせてください。
3. 【詰まりには一点だけの足場かけ】学生が混乱や詰まりを見せたときは、全体を解説し直すのではなく、
   詰まっている一点だけを短く補い、学生自身の言葉での言い直しで埋まったかを確かめてください。
4. 【質問と解釈が同居するとき】1つの発話に質問と解釈の表明が混在する場合は、まず質問の部分に
   完全な形で即答し（ルール1を優先）、そのうえで解釈の部分の言い直しと確認に入ってください
   （ルール2）。質問を保留にして言い直しから始めることはしないでください。

**共通ルール:**
5. 【学術ディスカッション調】雑談調にはしないでください。用語・論理展開を厳密に保ちつつ、
   一方的な講義にせず対話として書いてください。数式は LaTeX 記法（インライン $...$、
   ディスプレイ $$...$$）を使い、教材を参照した場合はコンテキストに付された番号付き出典
   マーカー `[出典1]` `[出典2]` … を本文に自然に挿入してください。
6. 【生成プロンプトの構造的必須化】回答の末尾には、必ず次のいずれか一つを添えてください
   （どちらか一つは毎回必須であり、気が向いたときだけ付ける確率的な付加は不可です）:
   - 学生自身の言葉での言い換え・予測・自己説明を促す短い誘い
   - why / how / what-if 型の問い返し（この結果が崩れるとしたら何が変わるか、等）
   いずれの場合も、学生の直前の発話の言葉を引用するか組み込んだ、その学生に固有の問いに
   してください。どの学生にも使い回せる汎用の決まり文句は不可です。
   なお、ルール2・3の言い直しのターンでは、「その理解で合っていますか」という確認の問い自体が
   この必須要素を満たします。確認の問いに、さらに別の why / how 型の問いを重ねないでください。
7. 【出所の正直さ】提供される「教材からのコンテキスト」に無い内容を話すときは、
   「これはこの論文に書かれている内容ではなく、一般的な学術知識からの補足ですが」
   のように、その部分がこの論文由来ではないことを一言明示してください。
8. 【数値を見せない】検索件数・一致度・網羅率のような数値スコアは出さないでください。{persona_block}
```

留意点:
- 「疑う」の命令形（「疑え」）は D層禁止語彙。プロンプト・UI とも「一緒に検討」の語彙を使う。
- 既存テストが要求するフレーズ（§2 DA6 のリスト）は全て上記本文に含まれている。
- ルール4（混在発話の優先順位）・ルール6 後段（言い直しターンでは確認の問いが必須要素を満たす）・
  ルール1 の「完全な形で」・「ギャップの地図」の修復完結は、いずれも 2026-07-31 のレビュー指摘
  F3/F4/F5/F7 への対応（§9 参照）。

### 5-1. 足場メッセージ（context 注入ターン）の中立化

システムプロンプトとは別に、`learning_chat` は LLM への最終メッセージ列に**全モード共通の
足場**を挟む（RAG コンテキストを載せる user ターンと、それを受ける assistant ターン）。
従来はこれが

> user: 「…上記のコンテキストを踏まえ…**以下の質問に答えてください**。」
> assistant: 「はい、「{topic_title}」についてですね。**お答えします**。」

という Q&A フレームを強制していた。system が「解釈には解説で応じない」と指示した直後に、
**発話直近の文脈**がこのフレームを再導入するため、学習者が立場を述べても完全解説が返る
（§0 の症状の再生産）。discuss のときだけ足場を中立化する:

> user: 「…上記のコンテキストを踏まえ（不足している場合は補完して）、
> **発話タイプ別の応答ルールに従って、以下の学生の発話に応じてください**。」
> assistant: 「はい。**学生の発話のタイプ（質問 / 解釈・立場の表明 / 詰まり）を見きわめて応じます**。」

- casual・通常（チューター）モードの足場は**変更しない**（既存挙動の維持）。
- 履歴ウィンドウ（`window_history` 20 messages / 2000 chars）は変更しない（§8-② 保留のまま）。

## 6. フロントエンド（discuss.js）

開幕画面の説明ノート（`.discuss-opening-note`）に、対話の流れを予告する一文を追加する:

> まず互いの読みを突き合わせてから、論文の主張を一緒に検討します。

- 目的: 序盤の「言い直し＋確認」往復が冗長に感じられないよう、学習者に進行の型を予告する。
- 数値・件数を含まない静的文言（DM6 適合）。局面のリアルタイム表示はしない（DA5、非スコープ参照）。
- モードバー「🗣 論文と議論中」は変更しない。

## 8. 非スコープ（v1）— 全項目保留（2026-07-31 オーナー確認済み）

いずれも「捨てる」ではなく**保留**。判断材料が出るまで着手しない。
①②の当面の判断材料は開発側の手動 E2E 観察（docker 実対話で局面逸脱・文脈喪失が
起きるかを見る）— 既存の discuss 観測基盤（migration 060）はエンゲージメントの
**量**（entered / opening クリック / 分岐チップ / 着地結果）しか記録せず、対話の
**質**は DO1（本文非含有）により計測できないため。

- **① サーバ側の局面状態機械・局面の DTO/API 追加**（DA5）— 保留。判断トリガー:
  E2E 観察で「係留を飛ばして解説に戻る」「共同検討に進まない」等の逸脱が観察されたら実装。
  観察されなければ不要（先回りの状態管理は保守負債）。
- **② 履歴ウィンドウ拡張**（学習チャット 20 messages / 2000 chars）— 保留。判断トリガー:
  係留確認が窓から落ちて中盤で噛み合わなくなる症状が実際に観察されたら拡張。
- **UI の局面チップ**（「いま: 理解の突き合わせ / 一緒に検討」）— ①に従属。局面状態
  なしで出すと推測表示＝不正直になるため、①を実装する判断をした場合にのみ検討する。
- **discuss 観測基盤への新イベント追加** — 保留。①②を**本番データ**で判断したくなった
  時点で最初に解除する項目（応答が確認型か解説型かの非LLMヒューリスティック判定を
  本文非含有・DO1 適合の kind として記録する等）。手動 E2E で足りる間は不要。
- **R層（再構成ループ）の構造 DIFF との接続** — 構想（実装予定リスト外）。
  「学習者の言い直し vs central_thesis」の構造照合。語彙は R層と揃えてあるため将来接続
  可能。やる場合は別 issue として起票し専用設計を切る。
