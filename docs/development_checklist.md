# 新機能 PR チェックリスト（開発運用規律）

[← ドキュメント目次](README.md)

新機能・機能変更の PR / 実装セッションで**毎回**確認する運用チェックリスト。
背景は `docs/architecture/vision_ux_gap_survey_2026-07-17.md` §5-5（ガイダンス機構の追随の
仕組み化）・§5-9（docs 運用の立て直し）・§6-6（2機能境界バグの教訓）。
「実装は正しいのに、案内・文書・境界テストが追随せず後から高コストで直す」パターンの再発防止が目的。

---

## 1. ガイダンス機構の追随（Copilot / KB / G層）

新しい画面・操作・API を足したら、**ユーザーへの案内系が追随しているか**を明記する
（不要なら「不要」と書く — 無言のスキップをしない）。

- [ ] **Admin Copilot capability**: 新操作は `backend/core/admin_assistant/capabilities.py`
      に登録が必要か？（登録する場合: `required_role` / `kind` / `reversible` /
      `confirm`（`reversible=false` は必ず `confirm=true`）/ `locate_steps` を宣言。
      fail-closed — 未登録の操作は Copilot が説明も代行もしない仕様であることを踏まえ、
      「今回は登録しない」の判断も PR に書く）
- [ ] **操作 KB**: `docs/admin_operations/*.md` に手順書を追加/更新したか？
      （front-matter `capability` / `role` / `screen` 付き。KB に無い操作は Copilot が
      「未整備」と答える）
- [ ] **G層 next_steps ルール**: 新機能に「次にやること」として案内すべき状態遷移が
      あるか？（`backend/core/admin_assistant/next_steps.py` のルールカタログ。
      G4「押し付けない」に反するルールは追加しない判断も明記）

## 2. docs 3点セットの更新有無を PR に明記

以下 3 つは陳腐化が最も速い「索引・正本」であり、更新の有無（と不要な理由）を
PR 説明に必ず書く。

- [ ] **CLAUDE.md**: 新レイヤー・新テーブル・新しい正本モジュール・開発ルールに影響が
      あるか？（新レイヤー追加時は該当節の新設が必須）
- [ ] **docs/architecture/layer_registry.md**: レイヤー行・migration 帰属一覧（§3）は
      実ファイル `backend/db/0NN_*.sql` と一致しているか？（migration を足したら §3 に
      1 行足す。「次の空き番号」の記述も更新）
- [ ] **README.md の機能ドキュメント索引**: `docs/features/` に設計書を追加したら
      索引にリンクを足したか？

設計書に書いた migration 番号が実装時にずれた場合は、**設計書冒頭に補正注記**を入れる
（例: W層設計書の「046 → 実装は 048/049」注記。一次情報は常に実ファイル名）。

## 3. 2機能境界の回帰テストを Definition of Done に含める

**教訓（survey §6-6）**: 2026-07-17 調査で見つかった高重大度バグ 4 件は、いずれも
単機能のテストでは検出できない「**2つの機能の境界**」で起きていた。新機能の DoD には
単体・ガードレールに加えて、以下の**型**に当てはまる境界の回帰テストを最低 1 本含める。

代表的な 3 つの型:

| 型 | 内容 | 例 |
|---|---|---|
| **設定保存 × 生成チェーン** | 設定・原稿の保存が、後段の生成（音声・スクリプト等）の前提と食い違わないか | 原稿編集後に旧音声が ready のまま配信される / 言語切替後に旧言語音声が残る |
| **再実行 × キャッシュ無効化** | 再解析・再生成が、前回結果のキャッシュ・投影・教員判断を正しく残す/消すか | 再解析が教員レビュー列を上書きする / 無効化すべきキャッシュが残る |
| **オプション × 前回 run 継承** | 実行オプション（analyze_images 等）が、前回 run の成果物の読み出しと混線しないか | オプション off の run で前回 on の artifact が最新として表示される |

チェック:

- [ ] 今回の変更が既存機能と接する境界を列挙したか（保存↔生成 / 再実行↔キャッシュ /
      オプション↔run 継承 / 権限↔投影 など）
- [ ] 上記の型に当てはまる境界に回帰テストを追加したか（当てはまる境界が無い場合は
      その旨を PR に明記）

## 4. アンカー整合（locate_steps ↔ registerUiAnchors）

Copilot の道案内（Locate & Spotlight）は、capability の `locate_steps[].anchor_id`
（論理 ID）をフロントの `registerUiAnchors` が DOM に解決して成立する。片側だけの
変更は**静かに壊れる**（案内が途中で止まる）。

- [ ] capability の `locate_steps` に新しい `anchor_id` を足した場合、対応する
      `registerUiAnchors` の登録（admin.js / admin-lecture-studio.js 等）を同じ PR で
      追加したか
- [ ] 画面の DOM 構造・タブ構成を変えた場合、既存 anchor の解決が壊れていないか
      （anchor を消す/改名する場合は capability 側も同時に更新）
- [ ] ガードレール（`backend/tests/test_admin_assistant.py` 系のアンカー整合検査）が
      新 anchor をカバーしているか

## 5. ドキュメント運用規約（2026-08-14 追加）

背景は [機能整備提案](architecture/feature_consolidation_proposals_2026-08-13.md) §1 と
[不具合報告](architecture/doc_review_findings_2026-08-13.md)。設計書（`*_design.md`）の
「実装後に §実装記録を追記」する運用は徹底されている一方、**機能解説・索引系の文書**には
規約が無く、大型機能が索引から丸ごと欠落した。以下 6 規約は PR レビューで照合できる形で
書いてある（該当しない場合は「該当なし」と PR に書く — 無言のスキップをしない）。

### 5-1. 機能解説ドキュメントの同時更新

変更の種類ごとに、更新すべき機能解説・索引を固定する。**設計書に書いただけでは満たさない**
（設計書は凍結される歴史記録であり、機能解説は現行の姿を示す文書）。

| 変更の種類 | 同時に更新する文書 |
|---|---|
| 学習者向け機能の追加・変更 | `docs/features/learning.md` の該当節 + `docs/backend/rag-chat.md`（チャット/RAG 経路に触る場合） |
| パイプラインステージの追加 | `docs/pipeline/overview.md` のステージ表 + `docs/pipeline/agents.md` の agent 節 |
| ルーター（`backend/api/routes/*.py`）の追加 | `docs/backend/api.md` |
| migration（`backend/db/0NN_*.sql`）の追加 | `docs/architecture/data-model.md` の表 + `docs/architecture/layer_registry.md` §3 |

- [ ] 上表の該当行の文書を同じ PR で更新したか（該当なしならその旨を明記）
- [ ] 機械検証（`backend/tests/test_docs_registry_guardrails.py`）が green か
      — migration 網羅 / ルーター網羅 / ステージ網羅 / 設計書⇄索引の孤児検出は
      このテストが担う。**テストが落ちたら文書側を直す**（テストを緩めない）

### 5-2. 設計書の状態ヘッダ必須

`docs/features/*.md` の冒頭（1500字以内）に、**ラベル付きの状態行**（「状態:」または
「ステータス:」で始まる行。`> **状態:** …` / `- ステータス: …` 等の装飾は自由）を必ず置く。
機械検証は `backend/tests/test_docs_registry_guardrails.py`（**ラベル行の存在のみ**を検査。
既存文書はレガシー凍結 allowlist で免除 — 減らす方向のみ）。`docs/architecture/*` の
調査記録にも同様の状態行を推奨する（機械検査の対象は features のみ）。

状態の値には次の 5 語彙のいずれかを**含める**（日付・migration 番号・括弧書きの補足は自由。
語彙の含有は機械検査せず PR レビューで確認する）。

| 状態 | 意味 |
|---|---|
| `設計中` | 実装前。内容は変わり得る |
| `実装済み（正本・凍結）` | 実装完了。以後は §実装記録の追記のみ（本文は歴史記録） |
| `生きたリファレンス` | 実装に追随して更新し続ける文書（`admin.md` / `auth-visibility.md` 等） |
| `提案（実装対象外）` | 提案止まり。着手時は専用設計書を切る |
| `調査記録（完了）` | ある時点の調査結果。**「本調査以降の変更は未評価」の定型文を必ず含める** |

- [ ] 新規文書に状態ヘッダを付けたか
- [ ] 実装完了で状態が変わる文書（`設計中` → `実装済み（正本・凍結）`）のヘッダを更新したか

### 5-3. レビュー・調査文書への解消注記

`*_review.md`・不具合報告・調査記録は、指摘が解消されても文面が「未修正」のまま残り、
読者が既知バグと誤認する。

- [ ] 指摘を解消したら、**レビュー・調査文書側に解消注記を追記**したか
      （設計書の changelog だけに書かない。該当箇所に「→ 2026-0N-NN 解消（実装先: …）」の形で足す）

### 5-4. 設計書に想定 migration 番号を書かない

設計時の「migration 0NN 想定」表記が、E層 034 衝突・W-β 046→048 ずれ・G層/状態通知の
相互矛盾する因果説明を生んだ。**一次情報は常に `backend/db/0NN_*.sql` の実ファイル名**。

- [ ] 設計書には「次の空き番号（実装時に採番）」とだけ書き、想定番号を書いていないか
- [ ] 実装後、設計書には**実際に採番した番号のみ**を記載したか
- [ ] 採番前に `ls backend/db/` で空き番号を確認したか（文書中の「次の空き番号」案内を信用しない）

### 5-5. リポジトリ外正本の禁止

`field_atlas_overlay_spec.md`（8文書が §番号付きで参照する「正本」）が一度もコミットされて
いなかった事故の再発防止。

- [ ] 「正本」と呼ぶ文書は `docs/` 配下に**コミットされて実在**するか
      （バッククォート参照・§番号付き参照も対象。リンク実在検査は
      `backend/tests/test_docs_registry_guardrails.py` と help_kb validator が担う）
- [ ] 未コミットの外部メモ・チャット履歴・ローカルファイルを正本として参照していないか

### 5-6. カウント値の記法

CLAUDE.md 内でアンカー件数の 4 値（228/244/248/255）が併存した事故の再発防止。
ドキュメント内の「N件」「N本」「N語彙」は次のどちらかに統一する。

- [ ] **(a) テスト固定値を参照**（「正確な件数は `backend/tests/test_xxx.py` が正」）か、
      **(b) 時点付き表記**（「2026-08-14 時点 N」）のどちらかになっているか
- [ ] 裸の数値（時点もテスト参照も無い「260件」）を新規に書いていないか

## 付記: このチェックリスト自体の位置づけ

- 本書は「実装の正しさ」ではなく「**追随と正直さ**」のチェックリストである。
  各項目は「やる」だけでなく「やらない理由を書く」ことでも満たせる（無言のスキップだけを
  禁止する）。
- レイヤー固有の不変条項（candidate-only / fail-closed / P4 / 数値非表示 等）は各層の
  ガードレールテストが構造的に守る。本書はその外側 — テストが守れない運用面 — を担う。
