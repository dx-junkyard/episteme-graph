# 新機能 PR チェックリスト（開発運用規律）

[← ドキュメント目次](README.md)

新機能・機能変更の PR / 実装セッションで**毎回**確認する運用チェックリスト。
背景は `docs/architecture/vision_ux_gap_survey_2026-07-17.md` §5-5（ガイダンス機構の追随の
仕組み化）・§5-9（docs 運用の立て直し）・§6-6（2機能境界バグの教訓）。
「実装は正しいのに、案内・文書・境界テストが追随せず後から高コストで直す」パターンの再発防止が目的。

---

## 1. ガイダンス機構の追随（Copilot / KB / G層）

新しい画面・操作・API を足したら、**ユーザーへの案内系が追随しているか**を明記する
（不要なら「不要」と書く — 無言のスキップをしない）。

- [ ] **Admin Copilot capability**: 新操作は `backend/core/admin_assistant/capabilities.py`
      に登録が必要か？（登録する場合: `required_role` / `kind` / `reversible` /
      `confirm`（`reversible=false` は必ず `confirm=true`）/ `locate_steps` を宣言。
      fail-closed — 未登録の操作は Copilot が説明も代行もしない仕様であることを踏まえ、
      「今回は登録しない」の判断も PR に書く）
- [ ] **操作 KB**: `docs/admin_operations/*.md` に手順書を追加/更新したか？
      （front-matter `capability` / `role` / `screen` 付き。KB に無い操作は Copilot が
      「未整備」と答える）
- [ ] **G層 next_steps ルール**: 新機能に「次にやること」として案内すべき状態遷移が
      あるか？（`backend/core/admin_assistant/next_steps.py` のルールカタログ。
      G4「押し付けない」に反するルールは追加しない判断も明記）

## 2. docs 3点セットの更新有無を PR に明記

以下 3 つは陳腐化が最も速い「索引・正本」であり、更新の有無（と不要な理由）を
PR 説明に必ず書く。

- [ ] **CLAUDE.md**: 新レイヤー・新テーブル・新しい正本モジュール・開発ルールに影響が
      あるか？（新レイヤー追加時は該当節の新設が必須）
- [ ] **docs/architecture/layer_registry.md**: レイヤー行・migration 帰属一覧（§3）は
      実ファイル `backend/db/0NN_*.sql` と一致しているか？（migration を足したら §3 に
      1 行足す。「次の空き番号」の記述も更新）
- [ ] **README.md の機能ドキュメント索引**: `docs/features/` に設計書を追加したら
      索引にリンクを足したか？

設計書に書いた migration 番号が実装時にずれた場合は、**設計書冒頭に補正注記**を入れる
（例: W層設計書の「046 → 実装は 048/049」注記。一次情報は常に実ファイル名）。

## 3. 2機能境界の回帰テストを Definition of Done に含める

**教訓（survey §6-6）**: 2026-07-17 調査で見つかった高重大度バグ 4 件は、いずれも
単機能のテストでは検出できない「**2つの機能の境界**」で起きていた。新機能の DoD には
単体・ガードレールに加えて、以下の**型**に当てはまる境界の回帰テストを最低 1 本含める。

代表的な 3 つの型:

| 型 | 内容 | 例 |
|---|---|---|
| **設定保存 × 生成チェーン** | 設定・原稿の保存が、後段の生成（音声・スクリプト等）の前提と食い違わないか | 原稿編集後に旧音声が ready のまま配信される / 言語切替後に旧言語音声が残る |
| **再実行 × キャッシュ無効化** | 再解析・再生成が、前回結果のキャッシュ・投影・教員判断を正しく残す/消すか | 再解析が教員レビュー列を上書きする / 無効化すべきキャッシュが残る |
| **オプション × 前回 run 継承** | 実行オプション（analyze_images 等）が、前回 run の成果物の読み出しと混線しないか | オプション off の run で前回 on の artifact が最新として表示される |

チェック:

- [ ] 今回の変更が既存機能と接する境界を列挙したか（保存↔生成 / 再実行↔キャッシュ /
      オプション↔run 継承 / 権限↔投影 など）
- [ ] 上記の型に当てはまる境界に回帰テストを追加したか（当てはまる境界が無い場合は
      その旨を PR に明記）

## 4. アンカー整合（locate_steps ↔ registerUiAnchors）

Copilot の道案内（Locate & Spotlight）は、capability の `locate_steps[].anchor_id`
（論理 ID）をフロントの `registerUiAnchors` が DOM に解決して成立する。片側だけの
変更は**静かに壊れる**（案内が途中で止まる）。

- [ ] capability の `locate_steps` に新しい `anchor_id` を足した場合、対応する
      `registerUiAnchors` の登録（admin.js / admin-lecture-studio.js 等）を同じ PR で
      追加したか
- [ ] 画面の DOM 構造・タブ構成を変えた場合、既存 anchor の解決が壊れていないか
      （anchor を消す/改名する場合は capability 側も同時に更新）
- [ ] ガードレール（`backend/tests/test_admin_assistant.py` 系のアンカー整合検査）が
      新 anchor をカバーしているか

## 付記: このチェックリスト自体の位置づけ

- 本書は「実装の正しさ」ではなく「**追随と正直さ**」のチェックリストである。
  各項目は「やる」だけでなく「やらない理由を書く」ことでも満たせる（無言のスキップだけを
  禁止する）。
- レイヤー固有の不変条項（candidate-only / fail-closed / P4 / 数値非表示 等）は各層の
  ガードレールテストが構造的に守る。本書はその外側 — テストが守れない運用面 — を担う。
