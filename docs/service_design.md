# episteme-graph サービスデザイン — ビジョンから UX への展開

**作成日:** 2026-08-23
**想定読者:** 外部ステークホルダー（研究室・大学・教育機関・資金提供者など、
本システムの背景と提供価値を初めて知る方）
**位置づけ:** [ビジョンと思想（正本）](vision.md) が「なぜこう設計するか（思想）」の正本、
各設計書（`docs/features/*.md`）が「どう作るか（機能要件・システム仕様）」の正本であるのに
対し、本書はその**間**を埋める: どのような現状認識・課題があり、ビジョンとの間にどんな
ギャップ（gap）を認め、それをどのような UX（体験）で解消しようとしているのかを、
一本の因果の鎖として整理する。


## §1 ビジョン（要約）

**研究の入り口に立つ学習者（大学院生）が、自分の理解のネットワークを、論文と分野の
公共的な知識ネットワークに重ねながら育てていける環境を作る。**

このシステムは PDF 論文を「構造化された知識」（概念・主張・数式・導出の連鎖・理論の
操作構造）へ自動変換し、その構造を土台に対話型・**産出型**の学習体験を提供する。
ゴールは「答えを配る」ことではない — AI が答えを配るほど、学習者自身の理解の産出は
細るからである。

ビジョンの根には一貫した知識観・学習観がある（詳細は [vision.md](vision.md) §2〜§5）:

- **知識は近傍との関係でのみ成り立つ** — 「全体の完成形」は存在せず、俯瞰の神の視点も作らない
- **検証と合意は別の軸** — 「みんなが認めている」と「確かめられている」を混同させない
- **理解は産出から始まる** — 開示の前に学習者自身の予測・再構成を挟む
- **AIは候補まで、確定は人間** — AI の出力は常に候補であり、確定の権限は学習者本人と教員に留保する
- **学習者は主権者** — 学習の痕跡は本人のみのもの。監視・評価には使わない

## §2 現状認識 — ステークホルダーと環境（2026-08 時点のスナップショット）

> 本節は日付つきのスナップショットであり、環境の変化に応じて大きな節目で改訂する（§8）。

### 2.1 学習者（大学院生・研究の入り口に立つ人）

- **論文は増え続け、読む時間は増えない。** 先行研究は分野をまたいで散在し、1本の論文が
  分野の中でどこに位置づくのか、他の論文とどの「部品」（概念・手法・数式）を共有して
  いるのかは、紙面のどこにも書かれていない。従来それを補ってきたのは研究室の徒弟的な
  対話だが、その機会は指導者の時間に強く依存する。
- **生成 AI の普及で「答え」は一瞬で手に入るようになった。** 要約も解説も式変形の確認も
  AI が代行できる。しかしそれは同時に、「分かった気になる」までの距離を縮め、
  学習者自身が予測し・再構成し・引っかかりを言語化するという**理解の産出過程**を
  スキップしやすくした。「式変形は追えるが物理が見えない」まま論文の表面をなぞる
  リスクは、AI 以前よりむしろ高まっている。
- 学習の過程で生まれる**問いや違和感** — 理解の最も貴重な副産物 — は、チャットの
  発話やノートの走り書きとともに流れ去り、本人の資産として蓄積されない。

### 2.2 教員（研究指導者）

- 指導に使える時間は限られ、教材の作成・更新のコストは高い。生成 AI は教材の下書きを
  量産できるが、**その品質を確認し、共有してよいと確定する作業**は依然として人間の
  仕事であり、生成量が増えるほどこの「確認の弁」がボトルネックになる。
- 学習者がどこでつまづいているかを知りたい一方で、学習ログの詳細な可視化は
  **監視・評価の装置**に転化しやすいことも知っている。支援と監視を分ける仕組みが
  ないまま学習データを扱うことには、教育的にも倫理的にもためらいがある。
- 同じ概念への理解・説明の仕方は教員ごとに異なる（それ自体が学術文化の豊かさである）が、
  既存ツールではどちらかの説明で上書きするか、共有を諦めるかになりがちである。

### 2.3 研究室・共同体

- 分野の知識の全体像（何が確立し、何が前提で、何が未検証か）は熟練者の頭の中にあり、
  形式知として共有されていない。「教科書に書いてある」と「実験的に確かめられている」の
  区別 — 研究者にとって死活的に重要な区別 — は、初学者からは見えない。
- 教員間で教材・解析結果を共有すると、今度は**共有物の更新・削除が受け手を壊す**
  問題が生まれる（引用した教材が黙って書き換わる・消える）。

### 2.4 既存ツールの環境

- **対話型 AI（ChatGPT 等）** は優れた「回答装置」だが、回答の根拠がどの文献に
  基づくのか（そもそも文献に基づくのか）の出所は保証されず、学習の産出過程を
  設計する装置ではない。
- **LMS（学習管理システム）** は進捗率・締切・成績を管理する装置であり、その数値化・
  ゲーミフィケーションの設計思想は、研究的理解の深さとは別の行動を最適化しがちである。
- **文献管理ツール**は保管と検索の装置であり、論文の**内部構造**（主張・導出・前提の
  つながり）や論文**間**の部品の共有関係には踏み込まない。

## §3 課題

§2 の現状から、本システムが取り組む課題を5つに整理する。

| # | 課題 | 誰の課題か |
|---|---|---|
| 課題1 | 散在する先行研究を、分野の中の位置と論文間のつながりとして**統合的に把握**できない | 学習者・共同体 |
| 課題2 | 生成 AI 時代に、**理解の産出過程**（予測・再構成・問い・違和感）を守り育てる学習環境がない | 学習者 |
| 課題3 | 「合意されていること」と「検証されていること」の区別、暗黙の前提の存在が、**構造として**見えない | 学習者・共同体 |
| 課題4 | AI が生成物を量産する時代の、**人間による確認・確定の弁**が制度としてもツールとしても未整備 | 教員 |
| 課題5 | 学習データの活用と、監視・評価への転化防止を**両立**する仕組みがない | 学習者・教員 |

## §4 Gap — ビジョンと現状の隙間

課題を「ビジョンが描く状態」と突き合わせると、埋めるべき gap は次の7つになる。

| ID | ビジョンが描く状態 | 現状 | gap（埋めるべき隙間） |
|---|---|---|---|
| **G1** | 論文が分野の地図の上に位置づき、論文間で共有される「部品」がたどれる | 位置づけとつながりは熟練者の暗黙知 | 論文を**構造**（概念・主張・数式・導出）に変換し、分野の座標系に重ねる手段がない |
| **G2** | 学習者が予測し、差分を見て、理解を更新する産出型の学習 | AI が答えを配り、産出過程がスキップされる | 「開示の前に産出を挟む」体験と、それを強制ではなく **opt-in** で提供する設計がない |
| **G3** | 問い・違和感が本人の理解の地図として蓄積し、再訪できる | 問いは発話とともに消える | 問いを「構造のどこに・どう引っかかったか」として**帰属付きで記録**し、本人だけの地図に育てる装置がない |
| **G4** | 「確かめられていること」と「合意されていること」が別の軸として見える | 両者は混同され、暗黙の前提は不可視 | 検証の範囲・反証の条件・前提の依存関係を**台帳**として記帳する制度がない |
| **G5** | AI が候補を量産し、人間が確定の弁を握る分業が回る | 確認作業が生成量に追いつかずボトルネック化 | AI 出力を「候補」の地位に固定し、教員の確認・確定を**効率よく・監査可能に**回す仕組みがない |
| **G6** | 学習の痕跡は本人の主権下にあり、教員には支援に必要な集約だけが届く | 学習ログ活用は監視・評価装置に転化しがち | 本人のみ可視の原則と**匿名化された集約**（少人数では表示しない等）を構造的に強制する仕組みがない |
| **G7** | 共有された知識・教材は、作り手の都合で受け手が壊されない | 共有物の更新・削除が引用者・受講者を壊す | 版の固定・削除の猶予・公開前の確認という**共有の作法**がツールに組み込まれていない |

## §5 UX — gap を埋めるために提供する体験

各 gap に対して、episteme-graph は次の体験を提供する。機能名ではなく
「利用者に何が起きるか」で記述する（対応する機能・設計書は §6 の表）。

### G1 → 「地図の上で学ぶ」

PDF をアップロードするだけで、論文は概念・主張・数式・導出の連鎖・理論の操作構造へ
自動的に構造化される。学習者は分野の地図（教員がレビューして凍結した骨格）の上で
「いまここ」を見ながら学び、論文がその地図のどこに置かれるかを確かめられる。
複数の論文に現れる同じ部品は「実は同じもの」としてリンクされ（各論文の表記は
書き換えない）、あるノードから隣の論文・分野の骨格・自分の過去の問いへと
**一歩ずつたどる「旅」**として探索できる。全体を一枚に描く俯瞰画面は意図的に作らない —
踏破率やカバー率の数値も出さない。地図は正解ではなく投影であり、「地図に置けない論文」は
エラーではなく、地図を育てる**発見の信号**として扱われる。

### G2 → 「開示の前に、自分の予測を置く」

学習者が望んだときだけ（明示的な精読モード）、続きを読む前に「次に何が導かれるか」を
予測として置ける。開示後の突き合わせは**採点しない** — 正解・点数・正答率は出さず、
本人の予測と出典の記述を並置し、「食い違いの可能性」を仮説の文体で示すだけである。
権威は常に出典（原文）にあり、AI の判定にはない。論文とは教材の順序に縛られず最初から
議論することもでき（「論文と話す」）、対話は答えの配布ではなく、学習者の解釈の
言い直し・確認・一点だけの足場かけという**歩調合わせ**で進む。セッションの終わりには
問いを持ち越して終え、次回はその問いから再開する。その間、システムは督促も通知もしない。

### G3 → 「問いと違和感が、わたしの地図になる」

学習中の質問は、質問文の保存ではなく「提示された構造の**どこに・どう**引っかかったか」
として記録される。AI は対話ログから「理解した上での引っかかり（違和感）」の候補を
見つけて提案するが、**それを違和感として確定するのは本人だけ**である。確定された問い・
違和感・再構成の成功は、本人だけが見られる「わたしの地図」に自動的に積み重なり、
過去の問いから今の学びへつながる道が示される。この地図は成績評価には使われない —
その注記が画面に常設される。

### G4 → 「何が確かめられ、何が前提かが読める」

すべての主張には「どの条件・どの範囲で確かめられたか」の台帳が付く。検証は○×の
一bitではなく**範囲の記述**であり、「証明済み」という全称の断定は構造的に書けない。
さらに「何が起これば覆るか」（反証条件）、「覆ればどこまで影響が届くか」、
「どこが一点の支持に吊られているか」まで記帳できる。台帳が言えるのは常に
「**このコーパスの中では**検証記録がない」までであり、「誰も検証していない」とは
言わない — 空欄は警告ではなく、次の検証提案・研究対話の出発点として提示される。
学習者にはこれらが読み取り専用の事実文として、未検証と検証済みを同じ精度で併記される。

### G5 → 「AIは候補を出し、教員が弁を握る」

AI の出力 — 抽出された主張、説明文、図の解析、地図への配置、同一性リンク — は
例外なく「候補」の地位で生まれ、根拠の逐語引用と理由を必ず伴う（根拠のない生成は
しない）。教員はレビューキューで候補を確認・却下し、確定の操作はすべて帰属付きで
監査記録に残る（匿名の承認・匿名の疑義は存在しない）。日々の確認作業は
「次にやること」の自動導出リストと画面横断の AI アシスタント（説明・道案内・代行）が
支える。同じ概念への複数の教員の説明は上書きではなく**並存**し、承認は説明の
バージョン単位で記録される。

### G6 → 「本人のみ可視、教員には匿名の集約だけ」

学習者の痕跡（問い・違和感・予測・意図）は本人のみが見られる。教員に届くのは
匿名化された集約だけで、該当者が少数の場合はそもそも表示されない（k-匿名の構造的
強制）。人数も正確な数値ではなく範囲で示す。個別の学習履歴を閲覧する経路は
存在せず、記録の削除も「消す」のではなく本人の意思表示（地図に反映しない等）の
状態遷移として保持される — 情報を落とさないことと本人の主権を両立する。

### G7 → 「共有には版があり、公開の前に確認がある」

教材・解析結果の共有は「発行版」の単位で行われ、受け手は発行版に固定された内容を
読む — 作り手が下書きを編集しても、発行するまで受け手には見えない。削除には猶予期間が
あり、受け手に事前通知される。コースの公開前には「AI が作ったものがこのまま学習者に
提示される」ことを教員が目で確認するステップが挟まり、確認の1操作が承認として
帰属付きで記録される。確認を飛ばしてもリリースは止まらない — ただし何が未確認かは
正直に示される。

## §7 機能要件・システム仕様への降り方

本書から先の詳細は、次の3段で整理されている。

1. **機能要件 + システム仕様**: 各設計書（`docs/features/*.md`）。機能ごとに
   「背景 → 不変条項（その機能が破ってはならない約束）→ データ構造 → API → 画面 →
   実装記録」を1枚に持つ。§6 の表のリンクが入口。
2. **アーキテクチャ全体像**: [docs/README.md](README.md)（システム構成図・技術スタック）と
   [レイヤー索引表](architecture/layer_registry.md)（機能層 ⇄ migration の索引）。

なお本プロジェクトの開発の型は「討論・調査（発散）→ UX 検討 → 専用設計書（不変条項の

設計書は実装後も仕様の正本として維持される。ドキュメントと実装の一致は機械検証
（ガードレールテスト）で構造的に守られている。
