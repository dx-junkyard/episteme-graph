# 課題ナレッジ（Issue Knowledge）

[← ドキュメント目次](../README.md) ｜ [分類体系](taxonomy.md) ｜ [記入様式](TEMPLATE.md) ｜ [辞書](dictionary.md) ｜ [索引](index.md)

> **状態:** 生きたリファレンス（2026-09-18 新設・同日改訂・2026-09-19 改善サイクル自身を対象に追加）。`docs/` で管理している課題（調査記録・レビュー
> 文書・是正リスト・設計書の残課題）から、**原因の性質による分類**・**発見の観点**・**解決の観点**
> を取り出して蓄え、あとで辞書として引ける形にする仕組み。分類は排他の箱ではなく
> **4 軸（処理・構造・接続・統制）の座標**で、群（局所 / 構造・接続・統制）は座標から導出する。機械検証は
> `backend/tests/test_issue_knowledge_guardrails.py`、索引の生成は
> `backend/scripts/issue_knowledge_index.py`。

---

## 1. 何のための仕組みか

これまで課題は、調査記録（`docs/architecture/*_survey*.md`・`six_lenses_*`）、レビュー文書
（`*_review*.md`・`doc_review_findings_*`）、設計書の「実装記録」「レビュー是正」節、
`CLAUDE.md` の各層節の追補、に**場所ごとの形式**で残っていた。どれも「何が壊れて、どう直したか」
は読めるが、次の 3 つが引けない。

1. **原因の性質**（4 軸の座標）で同型の課題を集めること（症状の場所や層で分かれてしまう）。
2. **どの見方をしたときに見つかったか**（発見観点）と**どの見立てで解けたか**（解決観点）。
3. 機能名を剥がした**課題の型**（辞書）と、その型が「どの機能を実現するときに出るか」。

**対象範囲の宣言**: 本仕組みが拾うのは **`docs/` に記録された課題**（調査・レビュー・是正リスト・
設計書の実装記録）である。テストの失敗や fix コミットだけで閉じた単一処理の不良は、docs に
記録が無いかぎり対象外。したがって局所の課題は構造的に少なく、それは欠陥ではなく範囲の帰結
（局所を拾いたければ、まず docs 側に記録を残す）。

**改善サイクル自身も対象に含める（2026-09-19 追加）**: コーディングエージェントが回す改善サイクル
（発見 → 選別 → 設計 → 実装 → 検証 → 是正 → 記録。正本は
[改善サイクル](../architecture/improvement_cycle.md)）の弱点 — 段の飛ばし・レビューの見逃し・同じ型の
再発・検証経路の欠落・手順の正本がリポジトリ外にあること — も、製品の課題と同じエントリ形式・同じ辞書で
記帳する。起票元は改善サイクル文書と各設計書の実装記録・レビュー是正節、層は [layers.md](layers.md) の
`cycle_*`。専用の仕組みは作らず、再帰は 1 段で止める（§3.5）。

本仕組みは、課題 1 件を 1 ファイルの**エントリ**（[TEMPLATE.md](TEMPLATE.md)）として、
[taxonomy.md](taxonomy.md) の語彙で記録し、[dictionary.md](dictionary.md) に型として畳む。
既存の調査記録・レビュー文書は**そのまま正本として残し**（`sources` で参照する）、本仕組みは
その上に載る索引層である。文書を移動・改変しない。

## 3. 運用手順

### 3.1 課題が新しく管理対象になったとき

1. 起票元（調査記録・レビュー文書・設計書の節・オーナー指摘の記録）が `docs/` に**実在**する
   ことを確認する。無ければ先にそちらを書く（本仕組みは索引層で、正本の代わりにはならない）。
2. `entries/` に次の番号で `IK-NNNN-*.md` を作り、[TEMPLATE.md](TEMPLATE.md) を埋める。
   - **原因を一文で書く**。症状ではなく原因を主語にする。
   - `classification.axes` を [taxonomy.md §1.2](taxonomy.md) の手順で決める（4 軸それぞれに
     「この軸の何かを変えなければ再発するか」を問い、無ければ `none`、見ていなければ `unknown`）。
     原因が未確定なら `cause_status: hypothesis` とし、`basis` を「仮説:」で始めて**何を確認すれば
     確定するか**を書く。
   - `discovery.perspective` に**どの見方で見えたか**を語彙で書く（誰が言ったかではなく、何と何を
     突き合わせたか）。
   - `feature_context.realizing` に**どの機能を実現しているときに出るか**を動詞の一文で書き、
     `generalization.general_form` に機能名・層名を剥がした型を書く。
   - `pattern` を辞書の型から選ぶ。畳めなければ辞書に型を 1 つ足す（§3.4）。
   - `feature_context.layers` は [layers.md](layers.md) の語彙から。観点は**最大 2 つ・先頭が主**。
   - AI が起こした分類は `classification.review: candidate` のまま置く。
3. 索引を再生成し、検証を通す。雛形は生成器の `--new <slug>` で次番号のファイルを作れる。

```bash
backend/.venv/bin/python backend/scripts/issue_knowledge_index.py
```

```bash
cd backend && .venv/bin/python -m pytest tests/test_issue_knowledge_guardrails.py -q
```

### 3.1b 分類を確定するとき（人のレビュー）

1. エントリの 4 軸の値・型・根拠文を読み、taxonomy §1.2 の手順で妥当なら
   `classification.review: confirmed` + `reviewed_by` + `reviewed_at` を書く。
2. 直すなら書き換えではなく `history` に旧値と理由を残してから変える。
3. 型の成立は確定エントリだけで数える。索引 §2 の「unknown の軸」と §3 の「暫定」「典型と実際の座標のずれ」が
   レビューの入口。

### 3.2 解決したとき

1. `status: resolved`・`resolved_at` を書き、`resolution.perspective` に**どの見立てで解決策に至ったか**
   （[taxonomy.md §5](taxonomy.md)・最大 2・先頭が主）、`landed_in` に着地先を書く。**解決済みには実在する
   コードのパスかコミットハッシュを最低 1 つ**（設計書・CLAUDE.md だけでは、どう解いたかを実装まで辿れない）。
2. 解決の過程で原因が確定・変化したら `cause_status` を `confirmed` に直し、分類が変わったなら
   `history` に旧値と理由を残す（**書き換えではなく追記** — 情報を落とさない）。
3. 起票元の調査記録・レビュー文書側にも解消注記を足す（[開発チェックリスト §5-3](../development_checklist.md)）。
   エントリは注記の代わりにならない。
4. 索引を再生成する。

### 3.3 分類で迷ったとき

- 複数の軸に当たる → **両方に値を置く**（排他ではない）。ただし各軸 2 値まで。「主に直した軸」は
  座標ではなく `resolution.perspective` に出る。
- 「文書の不具合」→ 安易に統制軸だけにしない。正本が複数ある（`structure: [aggregation]`）のか、
  更新手続が無い（`governance: [review]`）のか、両方か、原因で分ける。
- 「権限漏れ」→ 判定が無い（`processing: [logic]`）のか、判定結果が後段に伝わらない
  （`connection: [condition]`）のか、判定の置き場所が二重（`structure: [responsibility]`）なのか。
- 軸を見ていないなら `unknown` にして `hypothesis` に落とす。`none` は「見て無い」の記録。
- 場所（フロント／DB／層名）・行数・修正手段・発見経路で決めない（[taxonomy.md §1.2](taxonomy.md)。
  `basis` にそれらを書くと機械検査が弾く）。

### 3.3b 設計時に辞書を当てる（pre-mortem）

新機能・変更の設計時に、次の語が含まれるなら該当する族の型の「見分け方」を先に当てる
（[開発チェックリスト §6](../development_checklist.md)）。辞書を事後の記録から事前の検査に使う唯一の経路。

| 変更に含まれる語 | 先に当てる族 |
|---|---|
| 再実行・再解析・再生成・削除・全件再適用 | 再実行と削除（`reexecution-and-deletion`） |
| 既定値・プリフィル・自動確定・AI の判定 | 確定の担当（`human-decision-authority`） |
| 段階間の受け渡し・権限・可視性・オプション | 条件と対象の伝達（`condition-and-scope-transfer`） |
| キャッシュ・投影・音声・索引などの派生物 | 派生物と配線（`derivative-and-wiring`） |
| ID・キー・版・名前空間 | 同一性の表現（`identity-representation`） |
| 語彙表・判定・分割規則の新設 | 正本の分裂（`canonical-source-split`） |
| 外部 API・LLM 呼び出し | 順序と予算（`ordering-and-budget`） |

### 3.3c 体系を育てる（確信度 → 提案 → 暫定の値 → 再評価）

体系（軸の値）は最初から完全ではない。次の順で、事実に縛って育てる（[taxonomy.md §2.1〜2.4](taxonomy.md)）。

1. 各エントリは 4 軸に確信度（高・中・低）を付ける。低い軸には「新しい値か軸が要るか」を問い、
   要るなら `proposals` に 1 件書く（相手 = 境界が曖昧になる既存の値を必須）。
2. 索引 §12 が提案を「種別・軸・相手」で束ね、確信度 high が 3 件以上の束を**設定候補**として出す。
3. 人が taxonomy §2 に**暫定の値**として足し（相手の列を宣言・モジュール `PROVISIONAL_VALUES` に登録）、
   索引 §13 の**再評価キュー**（その値の相手に当たる軸で確信度が低いエントリ）だけを再評価する。
   全件は見直さない。連鎖は 1 段で止める。
4. 確定エントリ 2 件以上が使えば成立、使われなければ見送りを記録して残す。

### 3.5 改善サイクル自身の課題を記帳する（振り返り）

サイクルを閉じる（記録段）とき、[改善サイクル §3](../architecture/improvement_cycle.md) の起票条件
（段を飛ばした／検証後に見つかった欠陥がある／同じ型が再発した／検証経路が実運用を覆っていなかった／
手順の正本がリポジトリ外にあった）のいずれかに当たれば、1 件を §3.1 と同じ手順で起票する。

- `feature_context.layers` にサイクル層（`cycle_discovery` 〜 `cycle_recording`）を置く。層は場所の記録で、
  「レビュー段で見逃したから統制軸」のように**段の名前を分類の根拠にしない**。座標は原因の性質で決める。
- 起票元は改善サイクル文書・設計書の実装記録・レビュー是正節・調査記録の「着手の地図」。個人メモリや
  チャット履歴は起票元にならない（§5-5 と同じ）。
- 索引 §14「サイクルの計器」（型の再発・発見観点の月別分布・サイクル層のエントリ）が次のサイクルで
  弱い段を選ぶ材料になる。目標値にしない。

### 3.4 辞書に型を足すとき

1. 既存の型に畳めないことを確認する（`index.md` §3 の型別一覧を見る）。
2. [dictionary.md](dictionary.md) の該当する**族**（`###`）の下に `#### <slug>` と定義表を足す。族に
   畳めなければ族も足す（族は稀。原因の性質の大づかみな括りであり、課題ごとには作らない）。
   一般形には**機能名・層名・ファイル名を書かない**（型を機能から切り離すのが辞書の目的。
   「どの機能で出るか」はエントリの `feature_context.realizing` が持つ）。
3. エントリの `pattern` から参照する。参照の無い型は置けない（ガードレール）。

## 5. 規律（不変）

- **原因の性質で分類する**。症状の場所・修正行数・修正手段・発見経路で分類しない。
- **座標は記述、決定は解決観点**。排他の主分類を作らず、none と unknown を混ぜない。
- **体系の変更は事実に縛る**。値・軸の新設は 3 件以上の独立した提案が同じ相手を指したときだけ。新設後の再評価は相手の軸に絞る。
- **未確定は仮説と明示する**。`cause_status: hypothesis` は隠さず、索引でも仮説として区別される。
- **情報を落とさない**。エントリは削除せず `rejected` / `history` で残す。分類の変更は追記。
- **正本は起票元**。エントリは調査記録・レビュー文書・設計書の代わりにならない。`sources` は
  docs 配下に実在する文書だけ。
- **辞書は機能から切り離す**。型の一般形に機能名・層名・ファイル名を書かない。
- **索引は手で編集しない**。生成器の出力と一致することをテストが固定する。
- **数値で語らない**。件数は索引（機械生成）が持つ。エントリや辞書に「N 件」を手で書かない。
- **AI の分類は候補**。人が確定するまで型の成立に数えない（この仕組み自身が原則に従う）。
- **機械検査の限界**。検査できるのは語彙と構造だけで、根拠文の質（原因の性質を書いているか）は
  人の確定に委ねる。禁止記述の検出は正規表現で、誤検出・見逃しがある。
