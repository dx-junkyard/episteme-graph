## 課題

**症状**: 改善サイクル（調査 → 選別 → 設計 → 実装 → 検証 → 是正 → 記録）はコーディングエージェントが
毎回ほぼ同じ段を踏んで回しているが、段の順序と境界を宣言した文書がリポジトリに無い。選別の規律
（オーナーに問うのは 3 種だけ・推奨付きで束ねる）と実装の規律（UI なしの第 1 波を並列・第 2 波で
UI を集約・分割コミットの手順・サブエージェントへの禁止事項）はエージェントの個人メモリにしか無い。
サイクル自身の弱点（段の飛ばし・見逃し・CI が片経路）は、課題ナレッジが「製品の課題」を対象と
宣言しているため記帳先が無い。

**原因**: 課題ナレッジの対象範囲と層の語彙がサイクルを覆っておらず、サイクルの課題は語彙上の
居場所が無い。手順の正本が複数の文書と個人メモリに分散し、1 箇所で宣言されていない。サイクルを
閉じるときに振り返りを残す手続が無い。

軸ごとの判断: 構造軸は語彙の不在（representation）と正本の分散（aggregation）。統制軸は振り返りの
手続の不在（review）。処理軸には要素が無い。接続軸は none だが、見逃しが記録段へ運ばれない経路の
欠落とも読めるため確信度は中。

## 発見の観点

オーナーの問い（改善サイクルを部品に分け、課題ナレッジでサイクル自身も改善できないか）を受けて、
既存規約「リポジトリ外正本の禁止」とサイクル各段の正本の所在を突き合わせた（`invariant_audit`）。
段ごとの正本を列挙する棚卸し（`inventory`）で、個人メモリにしか無い規律と、課題ナレッジの対象範囲・
層語彙の欠けが同時に見えた。IK-0324 の統制軸の根拠文がサイクルの検証段への指摘そのものだったことが、
「すでに混ざって記録されているのに引けない」状態の証拠になった。

## 解決の観点

**正本の一本化**が主。段・入力・出力・手順の正本・計器を 1 文書に宣言し、個人メモリの規律をそこへ
移す。**宣言の明示**が従。対象範囲・層語彙・振り返りの起票条件・自律と人の線引き・再帰の上限を
文書と語彙表に書き、ガードレールで文書の実在と層の網羅を固定する。

解消方法として残す発見:
- 手順の課題を記帳できるかは、記帳の**対象範囲の宣言**と**語彙の居場所**で決まる。仕組みが製品の
  課題を扱えても、対象範囲に手順を含めなければ手順の弱点は黙って落ちる。
- 「正本はリポジトリに」という規約は、規約を運用する手順自身にも当てる。個人メモリは作業メモで
  あって正本ではない。
- 自己適用の再帰は 1 段で止める。サイクルの課題を製品の課題と同じ受け皿に入れれば、上の層は要らない。
- 同じ作業ツリーで 2 セッションが並走すると、片方のコミットが他方の途中のファイルを巻き込み、
  他方の未追跡ファイルが消えることがある。**並走するなら触るファイル集合を分け、コミット前に
  `git status` の全行を自分の変更か確認する**（本エントリ自身が一度消され、再作成された）。

## 一般化

「表現に居場所の無い情報が黙って削られる」型（`information-dropped-as-unrepresentable`）の一例。
ここで削られていたのは値や行ではなく、手順自身の不具合という種類の情報で、対象範囲と語彙に居場所が
無かった。辞書の典型座標（構造=representation / 接続=information）と違い、本件は構造=aggregation と
統制=review を伴う。手順・規約・運用ルールのように「実行者が人や AI である仕組み」を記録の対象に
含めるときに出る。
