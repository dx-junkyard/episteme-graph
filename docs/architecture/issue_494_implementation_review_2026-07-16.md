### 1. P1: 実際には完走していなくても「全トピックを学習」と表示される

対象:

- `frontend/public/js/app.js:2513-2514`
- `backend/api/routes/learning.py:1069-1168`

#### 問題

完了カードの表示条件は「現在のトピックに次のトピックがない」ことだけであり、全トピックの完了状態を確認していない。

サイドバーでは `locked` 状態のトピックにもクリックハンドラが付いているため、学習者は途中のトピックを飛ばして最終トピックへ移動できる。その状態で確認問題に回答すると、次の文言が表示される。

```text
学習を完了しました
「コース名」の全トピックを学習しました。
```

また、確認問題 API は採点結果を返すだけで、合格したトピックやコース完了状態を `learning_states` 等へ保存していない。したがって、完了状態は再読み込み後に復元できず、完了カードを繰り返し表示できる。

#### 影響

- 学習していないトピックがあっても完走と断定される。
- UI の事実文がサーバー状態と一致しない。
- 修了状態を再ログイン・別端末で復元できない。
- 将来、修了証明や次コース案内へ接続する際の正本状態が存在しない。

#### 修正方法

推奨対応:

1. `learning_states` に学習者ごとの完了トピック集合とコース完了日時を保存する。
2. 確認問題合格時に対象トピックを完了として記録する。
3. サーバー側で全対象トピックの完了を判定し、`course_completed` を返す。
4. `course_completed=true` の場合だけコース完了カードを表示する。
5. 前提トピック未完了時は、最終トピックへの遷移または完了判定を制限する。

永続化を今回のスコープに含めない場合の最小修正:

- 「学習を完了しました」「全トピックを学習しました」を削除する。
- 「最後のトピックの確認を終えました」など、現在確認できる事実だけを表示する。

#### 追加すべきテスト

- 最終トピックへ直接移動しても全コース完了にならないこと。
- 全トピック合格後だけ `course_completed=true` になること。
- 再読み込み後も完了状態が復元されること。

### 2. P1: 再構成レビューキューが複数教材コースの先頭教材しか対象にしない

対象:

- `frontend/public/js/admin-lecture-studio.js:1849-1863`
- `frontend/public/js/admin-lecture-studio.js:1898-1906`
- `frontend/public/js/admin-lecture-studio.js:1913-1934`

#### 問題

コースヘッダーの「再構成の確認」はコース全体の作業入口に見えるが、レビューキュー取得時は次の1件の `document_id` しか使用していない。

```javascript
var documentId = lsCurrentDocumentId() || lsCoursePrimaryDocumentId();
```

トピックまたは教材が未選択の状態では `lsCurrentDocumentId()` が先頭チャンクの文書を返すため、複数教材を含むコースでは2件目以降の再構成課題がバッジとモーダルの両方から欠落する。

加えて、件数バッジは `status === "auto"` かつ匿名性条件を満たす項目だけを数える一方、モーダルは API が返した `confirmed` / `retired` を含む全項目を「レビュー対象」として描画する。件数と一覧の母数が一致していない。

#### 影響

- 教員がレビューすべき課題を見落とす。
- コースに教材を追加するほど直行導線の網羅性が下がる。
- バッジが0件でもモーダルには処理済み項目が表示されるなど、表示が矛盾する。

#### 修正方法

推奨対応:

1. `GET /api/admin/reconstruction/items/review-queue` に権限検証付きの `course_id` フィルターを追加する。
2. コースの全 `sources` に属する claim/item をサーバー側で集約する。
3. 疑わしさ順のソートを全教材横断で行う。
4. API または UI で「要レビュー」の状態を明示し、バッジとモーダルで同一条件を使用する。
5. 処理済み項目を表示する場合は「履歴」へ分離し、「レビュー対象」と混在させない。

フロントだけで複数 `document_id` を並列取得して結合する方法もあるが、全教材横断の正しい並べ替えと権限判定を保つため、サーバー側の `course_id` 対応が望ましい。

#### 追加すべきテスト

- 2教材以上を含むコースで、各教材の要レビュー項目が一覧へ現れること。
- バッジ件数とモーダル内の要レビュー件数が一致すること。
- `confirmed` / `retired` が要レビュー一覧へ混入しないこと。

### 3. P2: コース切替後も前コースの候補カード・通知ドットが残る

対象:

- `frontend/public/js/app.js:2124-2153`
- `frontend/public/js/app.js:2156-2177`
- `frontend/public/js/app.js:3115-3146`

#### 問題

`switchCourse()` は次の状態をリセットしていない。

- `state.interestTraces`
- `state.tensionDigest`
- `state.anchorDigest`
- `state.tensionDeferred`
- `state.anchorDeferred`

一方、`loadInterestTraces()` は digest が `null` の場合だけ新しいコースの digest を取得する。そのため、コースAで候補を読み込んだ後にコースBへ切り替えると、コースAの候補カードと気づきドットがコースBの進捗タブに残る。

また、切替直前の非同期リクエストが遅れて完了すると、古いコースの応答で現在の state を上書きする可能性がある。

#### 影響

- 現在のコースと無関係な問い・違和感候補が表示される。
- 「候補到着」ドットの意味が不正確になる。
- コースを切り替えるほど状態の再現性が下がる。

#### 修正方法

1. `switchCourse()` の状態初期化で上記5項目を初期値へ戻す。
2. digest取得時に開始時点の `courseId` をローカル変数へ保持する。
3. 応答反映前に保持した `courseId` と現在の `state.courseId` が一致することを確認する。
4. コース切替後に現在コースの `interestTraces` / digestを明示的に再取得する。

#### 追加すべきテスト

- コースAの候補を読み込んだ後、コースBへ切り替えるとカードとドットが消えること。
- コースAの遅延応答がコースBのstateへ反映されないこと。

### 4. P2: 受講登録失敗後、同じコースを再試行できない

対象:

- `frontend/public/js/app.js:3091-3112`
- `frontend/public/js/app.js:3149-3160`

#### 問題

確認モーダルで「受講する」を選ぶと `enrollCourse(courseId)` が呼ばれるが、処理を `await` せず、成功・失敗を確認していない。

`enrollCourse()` は非2xx応答と例外を握りつぶすため、失敗した場合も select の値は `enroll:<course_id>` のまま残る。同じ option を再選択しても値が変化しないため `change` イベントが発生せず、別の option を一度選ばない限り再試行できない。

#### 影響

- 一時的な通信障害や409/500後に再試行しづらい。
- 失敗理由が表示されず、登録中なのか失敗したのか判断できない。
- 確認モーダル追加によるUX改善が、異常系では操作不能状態を作る。

#### 修正方法

1. `enrollCourse()` は非2xxで例外を送出し、成功時は `true` を返す。
2. 確認コールバックを `async` にして `await enrollCourse(courseId)` を実行する。
3. 失敗時は `select.value = prevVal` へ戻す。
4. 画面内に失敗理由と再試行案内を表示する。
5. 通信中は「受講する」ボタンを無効化して二重送信を防ぐ。

#### 追加すべきテスト

- enroll API が500を返した場合にselectが元へ戻ること。
- 失敗後、同じコースを再度選択して受講できること。
- 通信中の二重送信が発生しないこと。

### 5. P2: 再構成項目のPATCH失敗が成功扱いになる

対象:

- `frontend/public/js/admin-lecture-studio.js:1795-1809`
- `frontend/public/js/admin-lecture-studio.js:1942-1950`

#### 問題

共通関数 `lsPatchReconItemStatus()` は非2xx応答時に `null` を返す。

```javascript
return res.ok ? res.json() : null;
```

Promiseはrejectされないため、呼び出し側の成功ハンドラが実行され、一覧再取得・バッジ更新・キャッシュ破棄が行われる。エラーは表示されない。

#### 影響

- 403/404/409/422/500を利用者が認識できない。
- 操作が成功したように見えるが、再取得後に同じ項目が残る。
- 障害と未処理を区別するというIssue #494のG3方針に反する。

#### 修正方法

1. 非2xx時はレスポンスJSONの `detail` を取得する。
2. `throw new Error(detail || "更新に失敗しました")` でrejectする。
3. モーダル内の対象行にエラーを表示する。
4. 失敗時は操作ボタンを再有効化する。
5. 成功時だけ一覧・バッジ・キャッシュを更新する。

#### 追加すべきテスト

- PATCHが403/409/500を返した場合に成功処理が走らないこと。
- エラーメッセージが行内に表示されること。

### 6. P2: 同一性リンク確定・却下失敗時のエラー表示先が存在しない

対象:

- `frontend/public/js/deliberation.js:255`
- `frontend/public/js/deliberation.js:269-290`

#### 問題

同一性リンク行で描画しているエラー要素のクラスは次のとおり。

```html
<div class="deliberation-annotation-error"></div>
```

一方、確定・却下APIのcatch節は次のクラスを検索している。

```javascript
row.querySelector(".deliberation-identity-link-error")
```

クラス名が一致しないため、409/403/500や通信障害時に `errEl` は常に `null` となり、失敗理由が表示されない。

#### 影響

- 確定・却下が失敗しても利用者へ通知されない。
- ボタンは再有効化されるが、再試行すべき理由が分からない。
- 静的配線テストが存在しても実行時DOM契約の不一致を検出できていない。

#### 修正方法

- 描画側を `.deliberation-identity-link-error` に変更するか、catch側を `.deliberation-annotation-error` に変更してクラス名を統一する。
- 同一性リンク専用のクラスへ統一する方が、通常のannotationエラーと役割を分離できる。

#### 追加すべきテスト

- 確定APIが409を返した場合に詳細が表示されること。
- 403/500/通信例外でも汎用メッセージが表示されること。
- 失敗後に確定・却下ボタンが再有効化されること。
