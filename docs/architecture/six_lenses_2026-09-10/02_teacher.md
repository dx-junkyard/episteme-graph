### 1.3 表から読める構造的な事実

1. **弁は 25 種類以上あり、そのうち「必須」はコース公開だけ**。他の 24 は押さなくても
   学習者体験が成立する ＝ 押さないという選択が常にあるのは §4 の代替条件を満たす一方、
   **「押されないまま候補が溜まる」ことを教員が知る手段が無い**（後述 P3）。
2. **却下（切断）に理由が要るのは「地図系」5件だけ**（#14・#15・#16 と、確定側の #18・#19）。
   知識オブジェクト側の却下（#1 component / #2 claim / #6 説明 / #8 同一性リンク /
   #9 注釈 / #3 配置）は**全て理由なしで通る**。§2.7 が「切断は結合と対等の一級市民。
   理由と帰属を伴って結合と同資格で記帳される」（`docs/vision.md:126-130`）と書いた対象は
   まさにこちら側で、実装は逆になっている。
3. **前提の地図は確定に理由必須・却下は理由なし**という非対称に加え、UI が
   **確定理由に既定文をプリフィルしている**:
   `frontend/public/js/doubt-atlas.js:1280` — `window.prompt("確定の理由（既定文の選択に相当・追記可）:", "検出根拠を確認し、暗黙の前提として妥当と判断した")`。
   Enter を押すだけで「検出根拠を確認し…」という**確認した旨の文が本人の言葉として記帳される**。
   同 `:1297-1301` の却下は理由入力ゼロ。これは §4 の「人間のクリックを正当性と誤認しない」に
   最も正面から抵触する現物である（ゴム印の literal な実装）。
4. **`decision_context` は 4 経路だけ**（`core/decision_context.py:70-78` の basis 3語彙。
   実装は `element_explanations.py:383` / `landscape.py:630` / `atlas.py:1342`）。
   一括にもかかわらず付いていない経路が既にある（#24 `paper_discovery.py:573/695`）。
5. **監査が全く無い経路**が3つある: 版の adopt（`versioning.py:303`）、
   教材の物理削除（`admin.py:1665`）、原稿スタジオのトピック保存（`lecture_studio/topics.py:346`）。
   §6 原則14（監査必須）と §5.1（弁の操作はすべて帰属付きで記帳）に対する穴。
   削除は不可逆かつ学習者に届いている教材を消す操作で、**弁の中で最も重い**のに記帳が無い。
6. **承認と却下の視覚的な非対称が CSS レベルで存在する**: 深く検討（W層）の候補注釈カードは
   `.deliberation-annotation-btn.commit` が塗り潰しの青ボタン（`background:#378add;color:#fff`）、
   `.dismiss` が塗りなしのテキストボタン（`frontend/public/css/styles.css:7616-7631`）。
   同じ画面で「確定」だけが目立つ。逆に前提の地図は全ボタンが同一クラス `doubt-chip-btn` で対等、
   ランドスケープ・グラフレビューも同一クラス。**画面ごとにばらついている**。
7. **確認ダイアログの有無もばらついている**: 骨格凍結・ライブラリ凍結・コース公開・
   修正報告の採用は `openDangerConfirmModal` で事実文を出す（`admin.js:2493-2496, 5449, 6999-7009,
   10036-10066`）。一方、**リリース前の確認の「次へ」と最終「公開する」には確認が無く**
   （`admin-release-review.js:258-266, 642-671`）、component/claim 承認・配置確認・
   同一性リンク・候補注釈の単体確定にも無い。重さの順序と確認の有無が対応していない。
8. **ゴム印になりやすい弁の順位**（証拠に基づく私の判定）:
   ① 前提の確定（理由プリフィル）→ ② 説明の一括承認（200件・サーバが `evidence_shown=True` を断言）
   → ③ リリース前の確認「次へ」（根拠は折りたたみ既定・クライアント自己申告）
   → ④ claim 承認（1行1クリック・却下不可・「次の未レビューへ」で連打できる）。

## 2. 提案

### 提案1: 切断の一級化 — 却下に「理由」と「近傍」を持たせ、理由を再利用可能にする

**近づける vision の箇条**: §2.7（`docs/vision.md:126-134` 切断は結合と対等／免疫記憶は近傍ごと）、
§5.3（承認と疑義は対等）、原則8（出所の正直さ：切断の理由も理由付きで見せる）、原則14（帰属必須）。

**現状（証拠）**: 却下に理由が要るのは地図系5経路だけ（`core/atlas_reports.py:302`,
`core/atlas_gaps/store.py:693`, `atlas_edges.py:169-170`）。知識オブジェクト側は
`theory_components.py:3662`（body 無し）、`deliberation.py:636`、`element_explanations.py:326`、
`doubt.py:1419`（confirm は `doubt.py:1358` で理由必須なのに dismiss は無し）、
`landscape.py:311-314`（`review_note` 任意）。理由が要る5経路も UI は素の
`window.prompt("却下の理由（必須）")`（`admin.js:6096-6098` ギャップ / `:6528-6529` 辺 /
`:5442-5443` 修正報告）。**理由の再利用（過去の却下理由の選択・履歴）はリポジトリ全体に存在しない**
（フロント全 js を走査して reason picker / history のたぐいは0件。唯一の「再利用」は
`doubt-atlas.js:1280` の固定既定文プリフィル）。

**なぜギャップが体験を損なうか**: 却下に理由が要らないと、却下は「消す操作」に退化する。
教員は同じ種類の誤りを何度も却下するが、その判断は次の解析にも他の教員にも伝わらないため、
同じ候補が再び上がってきて同じクリックを繰り返す — 却下の労力が**蓄積せず消費されるだけ**になり、
結果として「全部承認して先へ進む」ほうが合理的な行動になる。逆に、理由を毎回自由記述させれば
負担で押し潰れる。§2.7 が「免疫記憶」と呼んだのは、まさにこの蓄積の仕組みである。

**機能のかたち**: (a) 却下・確定の視覚的重みを揃える（`styles.css:7616-7631` の
commit=塗り / dismiss=素 を、前提の地図の `doubt-chip-btn` 側に寄せる。§5.3 対等性の最小実装）。
(b) 却下系エンドポイントに `review_note`（必須）+ `dismiss_kind`（語彙）を
追加。語彙は**新規に発明せず** `core/label_vocab.py` に1表だけ追加する
（例: `evidence_missing` / `wrong_grain` / `not_the_same` / `out_of_scope` / `duplicate` /
`other`。`other` のみ自由記述必須）。(c) UI は**チップ1タップ + 任意追記**（`window.prompt`
自由記述に戻さない）。(d) 直近に自分が使った理由チップを先頭に出す（クライアント側の
localStorage で足りる。サーバに教員別設定テーブルを作らない）。(e) 却下理由は
`theory_review_events.metadata` に入るだけで、**共有地の負例集合にはしない**
（§2.7「共有地全体の負例集合を作らない」）。他の近傍へ伝播させるのは「近傍 A で
`not_the_same` として切られた」という来歴1行のみで、再解析の候補生成入力にはしない。
LLM なし・migration 不要（metadata JSONB）。`core/candidate_flow.py` は既に
`dismiss` を持つので、新規系統はそこへ接続する。

**14原則との照合**: 強めるのは原則8・14・§2.7。抵触リスクは**原則12（押し付けない）**と
**弁の収支**（却下1回あたりの手数が増える）。回避: チップ1タップで完了させ、
自由記述を必須にしない。手数の増分は提案3・4の削減で相殺する。

**規模感**: M（API 8本 + UI 6箇所 + label_vocab 1表。migration 不要）

### 提案2: 確定の来歴と「異議」を、確定の現場に置く

**近づける vision の箇条**: §5.3（`docs/vision.md:321-329` 重なるが同じではない理解の並存／
承認は説明バージョン単位）、§5.1（承認と疑義は対等の一級市民）、原則14（帰属記帳と開示の分離。
「帰属の開示が可視性勾配に従って遅れることは匿名ではない」= 逆に言えば**開示できる相手には
開示する**のが筋）。

**現状（証拠）**: 承認は `theory_review_events` に帰属付きで記帳されるが、
**教員向けにそれを読む API が存在しない**（`grep "FROM theory_review_events"` のヒットは
`atlas.py:1064` の COUNT、`core/doubt/metrics.py:65,109,122`（SYSTEM_ADMIN の KPI。
CLAUDE.md 記載のとおりダッシュボード UI 無し）、`core/help_kb/audit.py:83` のみ）。
グラフレビュー・深く検討の画面に承認者名は一切出ない
（`admin-graph-review.js` / `deliberation.js` に `reviewed_by` / 承認者の描画なし）。
承認者が見えるのは C層の説明カードだけで、それも**原稿スタジオ → 論理要素カード →
「説明・承認の共有」**という3階層下（`admin-lecture-studio.js:4794`, 承認者一覧は
`admin-lecture-studio.js:6884-6890` の `<details>`）。コース管理の共有ダッシュボード
（`admin.js:10086-10140`）は**作成者名**と承認の段階ラベル・引用数を出すが、
**誰が承認したかは出さず、疑義の情報も無く、反応するボタンが1つも無い**。
深く検討の「承認・共有」レンズ（`deliberation.js:320-329`）も読み取り専用の key/value 表。

「根拠を描画するコードが存在する」ことしか意味していない。これは §4 が最も避けたかった事態
——記帳が形式だけ整い、再構成しても「見たかどうか」が分からない——そのものである。
逆に、開いた/開かなかったを正直に残せば、記録は初めて再審の材料になる。

**機能のかたち**: (a) `decision_context` の `evidence_shown` を**サーバ断言では出さない**
（コード上の断言をやめ、`client_reported.evidence_expanded` に隔離。DC4 の趣旨に揃える）。
(b) フロントは「その行の根拠 `<details>` を開いた」という**実際の DOM イベント**だけを
集めて送る（滞在時間・視線などは測らない。開いた/開かなかったの2値のみ）。
(c) 1件も開かずに一括確定しようとしたときだけ、**阻止せずに**確認1行を出す:
「根拠を開かずに確定しようとしています。この確定は『根拠未展開』として記録されます。」
——押せば通る（原則12・RR7）。(d) 提案3の「わたしの弁の記録」に、その行が
「根拠未展開」だった事実を並記する。migration 不要・LLM なし。

**14原則との照合**: 強めるのは §4・原則8・DC4。抵触リスクは**原則5（監視しない）**の
教員版——教員の操作を測る計器になりうる。回避: **集計しない・他者に見せない・
本人の記録（提案3）にだけ残す**（§6.1「本人の資源・履歴は本人にだけ」）。
教員別の「根拠未展開率」のような指標は作らない（§6.1 の個人ランキング禁止をそのまま適用）。
指標カタログ（`core/indicator_catalog.py`）にも**登録しない**（値の宛先が本人だけで、
制度指標ではないため。推測: ここは設計時にオーナー裁定が要る）。

**規模感**: S〜M（`decision_context` 呼び出し3箇所とフロント2画面）

## 3. 見送った案

### (a) 未レビュー件数の G層 To-Do 化・バッジ化
「未レビューの component が N 件」を `next_steps.py` のルールに足す案。
**見送る理由**: 解析直後は常に大量に残るので**恒常点灯**し、消えない To-Do は督促に変わる
（原則12「押し付けない」/ G4「バッジは件数のみ・パネル自動表示禁止」の趣旨に反する）。
また件数の常時提示は §6.1 の「目標にせず、自動ゲートにしない」に近づく。
提案3(b) では**所在の事実文**（件数なし・既定で閉じている・dismiss で黙らせられる）に
留めることで、同じ情報要求を督促にせず満たす設計にした。

### (b) 承認しないと公開できないようにする（弁の必須化）
コース公開の前に未処理の弁をブロックする案。
**見送る理由**: リリース前の確認の不変条項 RR7（`docs/features/release_review_flow_design.md`、
実装は `landscape.py` の「権限の無いソース論文は 403 にせず静かに除外」等）と
§2.3「空欄は失敗ではなく発見」に正面から反する。未確認のまま出ることは正常な状態であり、
正しい対処は**止めること**ではなく**そう書くこと**（提案6(b) の所在の事実文と、
学習者側に既にある「AIによる推定（未確認）」ラベル）である。

### (c) AI による一次審査・承認推奨（「この10件は安全に承認できます」）
弁の総量を減らす最短の道に見えるが、**automation bias を最大化する**
（§4「自動助言は人間の正しい判断を覆すことがある」`docs/vision.md:245-247`）。
AI が「承認推奨」を付けた瞬間、教員の作業は根拠の検討から推奨の追認に変わり、
弁は形だけ残ってゴム印になる。弁の収支は**確定行為を賢く仕分ける**のではなく、
**重複を畳む（提案4）・所在を教える（提案3）・帰結を見せる（提案6）** で改善すべき。

### (d) 教員の確定件数・レビュー貢献度の可視化
「誰が何件承認したか」を出せば分担が進むという発想だが、§6.1 が禁じた
**個人を比較する数値**そのものになる（宛先「個人（他者を測る）」の行）。
提案2・4では**対象オブジェクト単位の来歴**（誰が確定したか）だけを出し、
**人単位の集計を作らない**ことで、分担の可視化と評価の回避を両立させた。
