## 2. 所見 — 偏りと空白

### 所見A: 学習者側は Explain に強く偏り、Elicit / Diff / Reflect は「1発話限りのボタン」に退避している

学習者宛の同期 LLM 10 経路のうち、常時稼働する既定は Explain 系（`chat` / `casual` / `discuss`）で、
Elicit / Diff は `cycle_mode` という**その1メッセージだけのフラグ**である。
`frontend/public/js/discuss.js:329-343` の「AIから問いをもらう」は定型文
「予想を立てる前に、考えるための問いを一つください。」を学習者の発話として送り、
直後のターンから既定の Explain に戻る。`discuss.js:288-297` の「AIに違いの観点を出してもらう」も同型。
理解サイクルは §3.1 で「一級の体験」と位置づけられているが、AI 側の配置は
**Explain 常設 + Elicit/Diff の押しボタン**であって、役割が対等に置かれていない。

### 所見B: 「検査」が置かれているのは教員側の D/SL 層と図解析だけで、**承認の瞬間には無い**

検査役割の LLM は `doubt:scope_candidates` / `doubt:falsification_conditions` /
`deliberation:standardization` / `apparatus_semantics(iterative)` の4本。いずれも
**承認画面とは別の場所**にある。実際の確定の弁 — component 承認・claim 承認・骨格凍結・配置確認 —
の直前に AI の否定側検査は一つも並置されていない:

- `api/routes/theory_components.py:3635 approve_theory_component` が呼ぶ検査は
  `_component_approval_problems`（`:3532-3557`）だけで、**構造的完全性（名前・出典・inputs/outputs の存在）**
  しか見ない。「この component の主張は backing claim の逐語と食い違っていないか」は誰も見ない。
- しかも承認時に `validation_warnings = CAST('[]' AS jsonb)`（`:3597`）で
  **解析時点の警告が消される**。人間が見ずに承認しても、見た証拠も見なかった証拠も残らない。
- グラフ全体対話の grounding には validation_results が入っている（`core/deliberation/graph_dialogue.py:345`）が、
  これは**教員が別タブでチャットに質問したときだけ**表に出る。承認ボタンの隣には無い。
- `decision_context`（§4 改訂原則1 の記帳）が付いているのは一括2経路のみで、単発承認には無い。

つまり §4 改訂原則1 の「確定者に提示された根拠・代替・**既知の不確実性**」のうち、
既知の不確実性が承認画面から構造的に落ちている。

### 所見C: Reflect は「非LLM で保存するだけ」で AI が一度も触れない

着地の reflection（`api/routes/learning.py:3364`, LLM 0 回）・帰還の扉の書き置き・
持ち越し問い・予想（`core/cycle/derive.py`）はいずれも本人の逐語をそのまま保存し、
以後の AI 経路の入力にも出力にもならない。tension mining はチャット発話しか見ず
（`core/tension/worker.py`）、structure_anchor worker の対象は `kind='question'` のみ。
**本人が最も意識的に書いた文（着地の一文）だけが構造に係留されないまま孤立する。**
§4 の役割行が Reflect を挙げているのに、対応する配置がゼロである。

### 所見D: 「形式化」が非LLM の部分文字列一致に委ねられている

自由記述 restate の DIFF は `core/reconstruction/diff.py:116 _covered` で、
concept 名の**部分文字列一致**である。日英混在・言い換え・記号表記が違えば必ず
`missing_concepts` に落ち、REFLECT が
「出典が触れている「◯◯」への言及が、あなたの版には見当たりません。」（`diff.py:174-177`）と
**事実文の形で断定する**。これは §2.5（表現の多様性は情報）に反する偽陰性であり、
§3.2 が禁じた「判定を authoritative に見せる」に事実上該当する。

### 所見E: AI の唯一の「即確定」が学習者側にある

`learning:understanding_check`（`api/routes/learning.py:1969`）は
①LLM に `{"passed": true/false, ...}` を返させ（`:1997`）
②`passed` が真なら `record_topic_check_pass` でトピック完了・コース完了を永続化し（`:2090`）
③偽なら `record_student_stumble_event(event_type="misconception")` に**学習者の回答逐語 + student_id**
を書く（`:2069`）
④LLM 失敗時のフォールバックは `passed = len(answer.strip()) >= 40` — **文字数による合否**（`:2045`）。

全 LLM 経路を見渡して、AI 出力がそのまま人間の状態を確定させるのはここだけである
（教員側の `admin:lecture_rewrite` の chunk 上書き `scripts.py:1058` が第二の例だが、
そちらは教員が続けて編集できる）。§3.2・§3.5・原則1・原則4改訂（自動ゲートにしない）に対する
最も強い不一致点。

### 所見F: 本人の資源が本人に見えない

学習チャットの CostGate は上限到達後に 429 + 事実文で初めて知らされる
（`api/routes/learning.py:246-256`）。フロントに残枠の表示・予告は無い
（`app.js` / `discuss.js` に 429 / 残数の扱い無し）。一方、教員には
`core/llm_usage/forecast.py` の「今日のAI利用枠に収まらない可能性があります」がある。
§6.1「本人 — 自分の資源（残りの注意・日次上限の残数）と履歴は本人にだけ見え、訂正できる」
に対して、学習者側だけ欠けている。

## 3. 提案

### 提案1: 確認問題の合否を AI の確定から外し、Elicit/Diff/自己確認に分解する

- **近づける vision**: §3.2（DIFF は採点しない・権威は出典）/ §3.5（演技化させない）/ §4 役割表 /
  原則1（改訂: 確定は人間の判断を含む手続に）/ 原則4改訂（自動ゲートにしない）
- **現状（事実）**: `api/routes/learning.py:1969` の `check_topic_understanding` が LLM に
  `passed: true/false` と `model_answer` を生成させ（プロンプト `:1997`「確認問題を採点する大学教員です」）、
  `passed` が真なら `record_topic_check_pass` でトピック完了・コース完了を `learning_states` に永続化する（`:2090`）。
  偽なら `record_student_stumble_event(event_type="misconception")` に回答逐語を書く（`:2069`）。
  LLM 例外時のフォールバックは `passed = len((body.answer or "").strip()) >= 40`（`:2045`）。
  応答 DTO は `passed: bool` を返す（`api/schemas.py:422`）。
- **なぜ体験を損なうか**: 学習者が自分の言葉で書いた瞬間に、AI が「合格/不合格」という
  二値の権威を行使し、その結果が進行状態として不可逆に書き込まれる。この一点だけで
  「AI は候補まで」という約束が学習者から見て嘘になり、以後の DIFF の仮説文体
  （「食い違いの可能性」）も演出に見える。さらに degraded 時に文字数で合否が決まるため、
  学習者は「長く書けば通る」という誤った戦略を学ぶ — これは §3.5 が禁じた演技化そのもの。
- **機能のかたち**: scene は `learning_chat` のまま。①`passed` の生成をプロンプトから外し、
  LLM は `answer_requirements` の各項目ごとに「触れられている / 触れられていない可能性」の
  **観点候補（最大3点・仮説文体）**だけを返す（Diff 役割）。②進行の確定は本人の
  「次に進む」ボタン（R層 SELF-CHECK と同型・非LLM）に移し、`record_topic_check_pass` の
  呼び出し元を本人操作にする。③degraded は文字数判定をやめ「AI の観点提示ができませんでした。
  出題の要件と自分の回答を見比べてください」+ 要件の並置に縮退（原則9 の degraded 規約）。
  ④`event_type="misconception"` の自動記帳は廃止（AI の判定を学習者の属性として書かない）。
  **migration 不要**（`progress_data` のキーは不変、書き込み契機だけ変える。DTO は
  `passed` を残しつつ `advisory: true` を足すか、`observations: []` へ置換）。
- **14原則との照合**: 原則1 ○（確定が本人に戻る）/ 原則9 ○（degraded が判定を生まない）/
  原則12 ○（押し付けない — 本人が進む）/ 原則5 ○（AI 判定由来の misconception 記帳が消える）。
- **規模**: M

### 提案2: 承認の直前に「AI が見つけた不一致」を並置する（Approval Inspector）

- **近づける vision**: §4 改訂原則1（AI は生成だけでなく**検査**も担いうる / 確定者に提示された
  根拠・代替・**既知の不確実性**を記帳）/ §5.1（弁がゴム印にならない条件）/ 原則2・原則8
- **現状（事実）**: `api/routes/theory_components.py:3635` の承認は
  `_component_approval_problems`（`:3532-3557`）＝名前・source_chunks・inputs/outputs の存在と
  出典欠落の**構造的完全性チェックのみ**。内容の突き合わせは行わない。
  承認時に `validation_warnings = CAST('[]' AS jsonb)`（`:3597`）で解析時の警告を消す。
  否定側の材料は `core/deliberation/graph_dialogue.py:345` の grounding に validation_results として
  入っているが、教員がチャットで質問したときだけ現れる。単発承認に `decision_context` は無い
  （`core/decision_context.py` の適用は一括2経路のみ — CLAUDE.md 記載、コードでも
  `release_review.placements` / `explanation_review.bulk` の2箇所）。
- **なぜ体験を損なうか**: 承認ボタンの隣に「疑う材料」が無い画面では、教員は AI が整えた
  肯定的な提示だけを見て押す。automation bias の教科書的条件が揃っており、押した後に
  警告列が空にされるので「何を見て承認したか」を後から再構成できない。§4 が
  「人間のクリックを正当性と誤認しない」ために課した条件が、まさに最も重い弁で満たされていない。
- **機能のかたち**: 非同期 worker を1本（`core/llm_worker/` の骨格 = 7系統目のアダプタ、
  `run_with_repair` + CostGate、feature `inspection:component_review`・fast tier）。
  対象は「source_backed だが未承認の component / claim」。プロンプトの課題は
  **否定側のみ**: 「component の inputs / outputs / summary のうち、backing claim の逐語と
  食い違う・逐語からは支持されない箇所を挙げよ。無ければ空配列」。
  evidence_quote verbatim 検査は既存の捏造ガードをそのまま流用。出力は
  `core/candidate_flow.py` に接続した candidate（格納先は `element_annotations` に
  `kind='inspection'` を1語追加するのが最小 — W層の既存 candidate 語彙・監査に相乗り）。
  承認 UI（`admin-graph-review.js` のノード詳細）に「AI が見つけた不一致（未確認）」区画を置き、
  `label_vocab.AI_READING_LABEL`（既存）を頭に付ける。承認 API は
  この区画に提示された findings の id 集合を `decision_context.presented` に積む
  （`build_decision_context` の既存契約に載る。`alternatives_available` は却下・再検討・後回しで既に満たす）。
  `validation_warnings` の消去はやめ、承認時は `review_reasons_at_analysis` と同型に**退避**する。
  **migration 必要**（`element_annotations.kind` CHECK に1語）。

### 提案3: 学習者の自然言語を構造へ「形式化」する候補経路（DIFF の前段）

- **近づける vision**: §4「AI は候補生成に限らず**形式化**にも使う」/ §2.5（表現の多様性は情報・

- **機能のかたち**: ①**即時の是正（非LLM・S）**: `build_reflection` の断定文を

- **14原則との照合**: 原則7 ◎（リンクであってマージではない）/ 原則1 ○（確定は本人）/
  原則9 ○（同期パスは非LLM のまま）/ 原則4 ○（confidence は返さない）/ 原則3 ○（原文保持）。

## 4. 見送った案

1. **学習チャットに自己批判ループ（self-RAG / 回答後の自動再検索）を入れる。**
   回答品質は上がりうるが、同期パスの LLM コールが2倍になり原則9（同期パスに LLM を入れない・
   1ターン1コール）と CostGate の設計を同時に崩す。検査は非同期に置く（提案2・7）方が
   ビジョンと整合する。

2. **痕跡から学習者の理解度を推定し、Elicit / Explain を自動で切り替える。**
   「回答装置に偏っている」の最短の解に見えるが、§3.6（沈黙適応をしない）と UC5/UC7 が
   名指しで禁じている。役割の切り替えは本人が選ぶ（提案4 の継続モード）か、
   本人が押す（現状の cycle_mode）以外に置かない。

3. **confidence が高い AI 候補を自動承認して教員の弁の総量を減らす。**
   §6.2 の「弁の収支」は魅力的だが、原則1 の改訂は逆方向（弁を減らすのではなく
   弁が実質的であるための条件を足す）を選んでいる。弁を畳むなら、承認対象そのものを
   減らす設計（例: 未承認でも配信できる範囲を明示する）で行うべきで、
   AI に確定を委譲する形では行わない。

4. **確認問題の採点をより良いモデル／より良いプロンプトに変える。**
   「モデルを変える」は本調査の対象外であり、かつ問題は精度ではなく
   **AI が確定者になっている配置**（所見E）である。提案1 は配置を変える。
