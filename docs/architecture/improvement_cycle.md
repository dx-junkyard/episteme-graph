# 改善サイクル（コーディングエージェントの運用規約）

[← ドキュメント目次](../README.md) ｜ [開発チェックリスト](../development_checklist.md) ｜ [課題ナレッジ](../issue_knowledge/README.md) ｜ [層の語彙](../issue_knowledge/layers.md)

> **状態:** 生きたリファレンス（2026-09-19 新設）。本書は**製品の機能ではなく、コーディングエージェント
> （Claude）が設計・実装・記録を改善するときに従う手順の正本**である。Python として実装するものは
> 無く、機械が触るのは課題ナレッジの索引生成器と語彙のガードレールだけ（§5・§7）。利用者から見える
> 変化はゼロ。段や規律を変えるときは本書を先に直す。

---

## 0. 位置づけ

- これまで改善サイクル（調査 → 選別 → 設計 → 実装 → 検証 → 是正 → 記録）は、
  [開発チェックリスト](../development_checklist.md)・`CLAUDE.md` 開発ルール・各設計書の「実装記録」節・
  エージェントの個人メモリに**分散した暗黙の手順**として回っていた。段の順序と境界を 1 つの文書で
  宣言したものが無く、選別（オーナー確認の絞り方）と実装（並列の波の分け方）の規律は個人メモリにしか
  無かった。これは [開発チェックリスト §5-5](../development_checklist.md)「リポジトリ外正本の禁止」に、
  サイクル自身が反していた状態である。
- 本書は段を名指しし、各段の入力・出力・正本・計器を宣言する。**新しい機構は足さない**。既存の
  チェックリスト・課題ナレッジ・ガードレールを段に割り付けるだけである。
- [課題ナレッジ](../issue_knowledge/README.md) は、これまで製品の課題だけを対象と宣言していた。本書の
  新設と同時に**改善サイクル自身の課題**も対象に加え（同 README §1）、サイクルの弱点を製品の課題と
  同じ形式・同じ辞書で記帳し、次のサイクルで直せるようにする（§3）。
- 個人メモリは作業メモであって正本ではない。正本にすべき規律が個人メモリにしか無いと気づいたら、
  本書か該当する規約文書に移す。

## 1. 段の宣言

| 段 | 入力 | 出力 | 手順の正本 | 計器（索引 = 課題ナレッジ index.md） |
|---|---|---|---|---|

| 選別・裁定 | 指摘の一覧 | 着手の地図（第 1 波・第 2 波・保留）、オーナー判断の束（推奨付き） | 本書 §2.2 | §8 未解決・保留 |
| 設計 | 着手項目 | 設計書（状態ヘッダ・不変条項・pre-mortem の族当て） | [開発チェックリスト §5-2 / §5-4 / §6](../development_checklist.md)、[課題ナレッジ README §3.3b](../issue_knowledge/README.md) | §3 型と実際の座標のずれ / §14 型の再発 |
| 実装 | 設計書 | コード・migration・テスト | `CLAUDE.md` 開発ルール、横断基盤の正本モジュール、本書 §2.4 | — |
| 検証 | 実装 | green のガードレール、CI の全経路、実 DB 実測、E2E の実施 / 未実施の記録 | 本書 §2.5 | §14 `guardrail_failure` の出現 |
| 是正 | レビュー指摘 | 設計書の「レビュー是正」節、起票元への解消注記 | [開発チェックリスト §5-3](../development_checklist.md) | §4 `adversarial_review` |
| 記録 | 全段の成果 | 機能解説・`CLAUDE.md` 追補・課題エントリ・**サイクルの振り返りエントリ** | [開発チェックリスト §5 / §6](../development_checklist.md)、`CLAUDE.md` 開発ルール 8・9 | §0 分類の確定状態 / §14 サイクル層のエントリ |
| 体系の育成 | 確信度の低い軸・新設の提案 | 暫定の値・再評価 | [taxonomy §2.1〜2.4](../issue_knowledge/taxonomy.md) | §11〜§13 |

段は順に踏むが、飛ばすことはある。**飛ばしたときは飛ばしたと書く**（無言のスキップだけを禁じる —
チェックリスト付記と同じ規律）。飛ばした段は記録段で振り返りエントリの候補になる（§3）。

## 2. 各段の規律

### 2.1 発見

- 発見の観点は [taxonomy §4](../issue_knowledge/taxonomy.md) の語彙で書き、**誰が言ったかではなく何と何を
  突き合わせたか**で残す。
- 索引 §14 の観点分布を見て、続けて使っていない観点（実データの読み・再現・棚卸しなど）を次の調査で
  意図的に使う。同じ観点だけで見続けると同じ型しか見えない。
- 外部 API（arXiv 等）は調査でも最小回数。到達性の切り分けは 1 回で止める。

### 2.2 選別・裁定

- **オーナーに問うのは 3 種だけ**: ①不変条項の解釈変更（例外・適用範囲の移動）②人の権利・制度・法
  （個人データ・同意・可視性）③後戻りしにくい構造（正本テーブルの意味論）。原則違反の是正・実装方式・
  順序・命名・規模の切り方・正本モジュールが決まっている選択は問わずに進める。
- 問うときは必ず推奨を付け、同じ原因を共有する項目は 1 つの判断に束ねる。前回「保留」でも原則から
  一意に決まるものは決定として宣言し、異論があれば一言で止められる形にする。
- 選別の結果は設計書の末尾（オーナー判断表）か調査記録の「着手の地図」に書く。個人メモリだけに残さない。

### 2.3 設計

- 設計書には状態ヘッダを付け、想定 migration 番号を書かない（チェックリスト §5-2 / §5-4）。
- **pre-mortem**: 変更に「再実行・削除・既定値・AI の判定・段階間の受け渡し・派生物・ID や版・語彙表の
  新設・外部呼び出し」が含まれるなら、辞書の該当する族の「見分け方」を先に当てる（課題ナレッジ
  README §3.3b）。該当しないなら「該当なし」と書く。
- 新しい外部呼び出しを足すときは「一連の操作で何回叩くか」の予算表を設計書に書く。

### 2.4 実装

- 並列で実装するときは**第 1 波 = UI に触らないバックエンドを並列、第 2 波 = UI・アンカー・マニュアルを
  1 体に集約**。共有ファイル（`admin.js`・アンカー表・`services.py` 等）を複数体が同時に触らない。
- 共有ファイルをハンク単位で分割コミットするときは、文脈ゼロの適用（`-U0`）を使わない。HEAD に
  `-U3` のパッチを当てて index blob を作り、コミット後はクリーンな HEAD で構文検査とテストを回す。
- サブエージェントへの指示に明記する禁止事項: `git stash`、実 DB への破壊的操作（CREATE / DROP
  DATABASE・孤児 DELETE）、外部 API の live 呼び出し。実機検証は指揮側が担う。
- A 層（`src/episteme_graph/agents/`）非改変、横断基盤の正本モジュール（`CLAUDE.md`「横断基盤」節）を
  使い同型実装をコピペしない、という既存規律はそのまま効く。

### 2.5 検証

- ガードレール・ユニットテストの green は前提であって完了条件ではない。**実行経路が複数あるなら
  全経路を CI で流す**（migration は psql 経路とランナー経路の両方、など）。
- 実 DB で意味が変わる変更（migration・supersede・掃除）は複製 DB か scratch DB で実測する。
- docker E2E を実施したか否かを記録に残す。未実施のまま閉じるなら「未実施」と書く（後日の振り返り
  エントリの根拠になる）。

### 2.6 是正

- 実装後に「壊すつもりで」読む敵対的レビューを 1 回置く。指摘は設計書の「レビュー是正」節に、
  解消は起票元の調査記録・レビュー文書にも注記する（チェックリスト §5-3）。
- 是正で原因の性質が変わったなら、課題エントリの座標を `history` に追記して直す（書き換えない）。

### 2.7 記録

- チェックリスト §5-1〜5-6・§6 に従う。課題は 1 課題 = 1 エントリで課題ナレッジへ。
- **サイクルを閉じるときに振り返りエントリを起票する**（§3）。
- `CLAUDE.md` への追補は「現行の姿」だけを書き、件数はテスト参照か時点付きにする。

### 2.8 体系の育成

- 課題ナレッジの体系（軸の値・辞書の型）は [taxonomy §2.1〜2.4](../issue_knowledge/taxonomy.md) の手続で
  育てる。確信度 → 提案の束 → 人が暫定の値を足す → 相手の軸だけ再評価。再評価の連鎖は 1 段で止める。

## 3. 自己適用 — サイクル自身の課題を記帳する

改善サイクルの弱点は、製品の課題と同じエントリ形式・同じ辞書で
[課題ナレッジ](../issue_knowledge/README.md) に記帳する。専用の仕組みを作らない。

- **起票元**: 本書（§7 の記録）、各設計書の「実装記録」「レビュー是正」節、調査記録の「着手の地図」。
  課題ナレッジの規律「正本は起票元」はそのまま守る。
- **層**: `feature_context.layers` に [layers.md](../issue_knowledge/layers.md) のサイクル層
  （`cycle_discovery` / `cycle_triage` / `cycle_design` / `cycle_implementation` / `cycle_verification` /
  `cycle_remediation` / `cycle_recording`）を書く。層は**場所の記録**であって分類の根拠ではない —
  「レビュー段で見逃したから統制軸」とはしない。座標は原因の性質（例: 検証経路が片方しか無かった =
  接続軸の契約 / 完了判定が緩い = 統制軸の completion）で決める。
- **振り返りエントリの起票条件**: サイクルを閉じる（記録段）とき、次のいずれかに「はい」なら 1 エントリ。
  1. 段を飛ばした、または「未実施」と書いて閉じた（E2E・敵対的レビュー・pre-mortem など）。
  2. レビュー・検証を通ったあとで見つかった欠陥がある（見逃し）。
  3. 辞書の同じ型が再発した（pre-mortem の族当てが効いていない可能性）。
  4. 検証の経路が実運用の経路を覆っていなかった。
  5. 手順の正本がリポジトリ外（個人メモリ・チャット履歴）にしか無かった。
- **再帰は 1 段で止める**。サイクルの課題は製品の課題と同じ受け皿に入れ、「サイクルを改善する
  サイクルを改善する」層は作らない（taxonomy §2.4 が再評価の連鎖を 1 段で止めるのと同じ理由）。

## 4. 自律と人の線引き

製品側の「AI は候補まで・確定は人」（vision §6 原則 1）をサイクル自身にも適用する。

| エージェントが自律で行う | 人（オーナー）が裁定する |
|---|---|
| 発見（観点調査・レビュー・実測）と候補としての起票 | 課題エントリの分類の確定（`classification.review: confirmed`） |
| 新設の提案を束ねて設定候補を提示する | 体系（軸の値・辞書の族）の変更 |
| 索引の計器を読み、次のサイクルで使う観点・当てる族を選ぶ | 本書の段・規律の改編 |
| 振り返りエントリの起票 | §2.2 の 3 種の判断 |

確定の詰まり（候補が積もって型が成立しない）は、自律化で解かず、確定の入口を索引 §11・§12 に絞る
ことで人の負荷を下げる。確定を AI に移す提案は §2.2 ①（不変条項の解釈変更）に当たり、人が裁定する。

## 5. 計器の読み方（索引 §14）

数値は索引（機械生成）だけが持つ。本書にもエントリにも件数を書かない。**目標値・KPI にしない**
（制度指標カタログ IG3 と同型 — 個人ランキングも自動ゲートも作らない）。

| 索引の節 | 読み | 次のサイクルでの使い方 |
|---|---|---|
| §14 型の再発（月別） | 同じ型が月をまたいで出続ける | その族の pre-mortem を設計段で必ず当てる。辞書の「見分け方」を補う |
| §14 発見観点の月別分布 | 特定の観点に偏っている | 使っていない観点を次の調査で意図的に使う |
| §14 サイクル層のエントリ | 未解決のサイクル課題 | 次のサイクルの冒頭で読み、着手の地図に載せる |
| §4 `guardrail_failure` / §14 | 検証段の失敗が起点の課題 | 検証経路の欠落（CI が片経路など）を疑う |
| §0 分類の確定状態 | 候補が積もっている | 人の確定の入口を §11・§12 に絞って提示する |
| §10 出典被覆 | 調査文書から拾えていない | 記録段で記帳漏れを埋める |

## 6. 非スコープ

- 製品の機能・API・テーブル・UI への追加（利用者から見える変化は無い）。
- サイクルを実行する Python コード（ワークフロー自動実行・自動起票）。機械が触るのは索引生成器と
  語彙のガードレールだけ。
- サイクル自身の KPI・目標値・進捗率。
- 「サイクルを改善するサイクル」のさらに上の層（§3 の再帰 1 段）。
- 分類の確定・体系の変更・本書の改編の自律化（§4）。
