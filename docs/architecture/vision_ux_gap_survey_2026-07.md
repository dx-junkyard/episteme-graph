## 0. エグゼクティブサマリー

最重要の発見は次の 5 点。

1. **【幹線断絶】学生が教員のコースに到達する 2 経路が、UI レベルで両方塞がっている。**
   - 公開経路: `PUT /courses/{id}/publish` は意図的に撤去済み
     （`test_course_group_permissions.py:207` の `test_publish_endpoint_removed` が撤去を固定）。
     後継の `PUT /courses/{id}/visibility`（public 指定で `is_published=true` になる。
     `admin.py:1076`）はサーバに存在するが、**フロント JS 全体から `/visibility` を呼ぶコードが
     ゼロ**。コース管理タブに公開ボタン自体が無い。
   - グループ経路: 管理者の直接招待も学生本人の承諾（`POST /api/me/invitations/{id}/accept`）が
     必須だが（`groups.py:353-`）、学習 UI 側は `app.js` に `initApp()` が二重定義されており
     （`app.js:3204` と `app.js:4511`、後者が勝つ）、`initGroups()` / `loadInvitationBadge()` を
     呼ぶ前者がデッドコード化。**「グループ」ボタンは押しても何も起きず、招待の承諾・招待
     コード参加が UI から一切できない。**
   - 結果として、ミッションの根幹である「教員が作ったコースで大学院生が学ぶ」というハンドオフが、
     現状 curl / Swagger を使わない限り成立しない。
2. **【実装済み未配達】バックエンド完成・フロント接続ゼロの機能群が層単位で存在する。**
   U 層（LLM 使用量）はフロントに文字列すら無い。個人知識ネットワーク Phase B の教員窓口
   `bridge-insights`、D 層の `verification_status` 記帳（設計思想の心臓部「確定は人間」の実行手段）、
   C 層 sharing-dashboard、W 層の identity-links / 標準化アセスメントも未接続。
   約 70〜80 エンドポイントが未呼び出し。
3. **【思想の副作用】fail-closed + 「押し付けない」原則が、初期状態の学習者に「ほぼ空の画面」を
   見せる。** 地図・digest・台帳・再構成はすべて条件成立まで黙って消える設計で、「候補なし」
   「未処理」「権限なし」「障害」の区別が UI 上つかない。ビジョンの中核体験（tension 確認・
   再構成・旅）はデータと時間が貯まるまで存在に気づけない。
4. **【認知負荷】教員側は 13 タブ・約 19 モーダルに機能が層別縦割りで散在し、1 つの理論
   コンポーネントを「片付ける」のに最大 6 箇所を巡回する。** それを緩和するはずの
   Admin Copilot は capability 15 件、G 層 next-steps はルール 6 件で、C/D/R/W/L/V 層を
   カバーしておらず、しかも存在しない公開ボタンへ案内し続ける。
5. **【ビジョン未完部分の明示】E 層（段階的翻訳）が未実装のため「入門者が手に取れる」という
   約束は未達。旅はコース内限定、Phase B は片肺（教員側 UI なし）。これらは設計上の意図的
   先送りだが、ビジョン文書はすでに約束として書かれている。**

## 1. ビジョンが約束している体験（要約）

詳細な抽出は調査①の成果物にあるが、UX 評価の基準として要点のみ:

- **学習者への約束**: 自分だけの理解ネットワーク（わたしの地図）を持てる／理論を自ら再構成して
  構造とのズレを突きつけられる（スコアなし）／違和感・問いを断定されずに自分のペースで確定
  できる／未検証と検証済みを同じ精度で併記される／明示操作で知識の「旅」に出られる。
- **教員への約束**: 任意の要素を文脈の中で深掘り・検討できる（W 層）／同一性整理は非破壊リンク
  （KN-2/3）／「次にやること」だけが押し付けずに示される（G 層）／つまづきを k-匿名集約で見て
  説明改善に使える／検証スコープの記帳が正式な学術行為になる（D 層）／共有物は版で保護される（V 層）。
- **UX に直接効く不変条項**: 神の視点を作らない（KN-1）／数値を見せない／candidate は本人確定
  まで見せない／k=3 匿名（少人数コースでは集計自体が消える）／fail-closed（想定外は
  エラーでなく非表示）／情報を落とさない（P4）／自動で開かない・ポーリングしない。

これらの原則自体は実装に一貫して守られている（ガードレールテスト群が構造的に固定）。
**問題は原則の違反ではなく、①原則が要求する「人間の確定操作」の UI が欠けていること、
②原則の副作用（非表示・非通知）を補う設計が無いこと**に集中している。

### G3. fail-closed の副作用 — 「空」と「壊れ」の区別がつかない【重大度: 中】

fail-closed・k-匿名・candidate 非表示は意図した設計だが、**初期状態や障害時に「何も起きて
いない」ことと「機能が壊れている」ことをユーザーが区別できない**という共通の副作用がある。

- 地図（Field Atlas）: 骨格なし/binding 不成立で「地図」ボタン・ミニマップ・cue・コースビュー版
  わたしの地図が**すべて黙って消える**（atlas-data.js:66-93 → atlas-overlay.js:629-633）。
- tension / anchor digest: worker 未実行・confidence<0.55 では「進捗」タブに何も出ず、
  「準備中」表示すら無い（learning.py:1967-1995、app.js:1972-2023）。
- 台帳一行表示・未検証前提リスト: 404 で沈黙（app.js:1156-1175, 1924-1946）。
- 再構成: 「まだありません」とは出るが、なぜ無いか・いつ増えるかの説明なし（reconstruction.js:82-89）。
- 通信障害も同じ経路で握りつぶされる: personal-map 系は 401/404/例外を全て null に丸めて非表示
  （personal-map.js:106-119）、doubt-atlas.js は `.catch(function(){})` で無言失敗
  （doubt-atlas.js:222-225, 326 付近）、atlas-cues.js も同様。
- 構造依存の落とし穴: コースビュー版「わたしの地図」（P-1）は地図オーバーレイの**内部に
  ネスト**しており、地図が使えないコースでは巻き添えで到達不能になる（atlas-overlay.js:88-157,
  543-551。P-3 のトップバー版のみ生存）。

### G4. 発見可能性 — ビジョンの中核体験が埋もれている【重大度: 中】

- **tension / anchor digest**（「そう、これ」の確定体験＝B 層の心臓部）は「進捗」タブ
  （既定非表示）内の「問いの軌跡」セクション先頭にあり、タブのドット表示は revisited しか
  見ないため候補到着を知る手段が無い（app.js:2025, 2105）。
- **R 層レビューキュー**（教員）はスタジオ→コース→トピック→右ペイン切替→claim カード展開の
  **5 段階**の奥。到達前にバッジなし（admin-lecture-studio.js:1605-1770）。
- ambient 通知は V 層の🔔のみ。C/D/R/L 層の滞留作業（承認待ち・未確認前提・疑義・レビュー
  キュー・未凍結ドラフト）にバッジが一切無く、「タブを開いた人だけが見る」設計。
- 受講可能コースの `description` は API が返しているのに UI が表示せず（learning.py:203 ほか、
  renderCourseSelect app.js:2935-2963）、学習者は概要を見ずに受講する。
- レクチャーボタンの無効理由はツールチップのみ（app.js:3478-3484）。

### G5. 教員側の認知負荷と縦割り【重大度: 中】

- TEACHER が到達可能な管理タブ **13 個**（+動的 2 個）、独立モーダル **約 19 種**、教材テーブル
  1 行に **7 系統のボタン群**、パイプラインメニューは内部 agent 名がそのまま並ぶ **21 項目**
  （`DocumentStructureAgent` 等。admin.js:293-340）。
- 同一の theory_component への操作が場所により異なる: カード（承認/却下/共有/深く検討の
  6 ボタン、admin-lecture-studio.js:2826-2833）とグラフノード詳細（承認系ボタン**なし**、
  同 3600-3712）で「見る画面」と「操作する画面」が分離。1 コンポーネントの決着に最大 6 箇所。
- 「共有」概念の重複: グループ共有（openDocumentShareModal / openPermissionModal——コード上
  ほぼ複製と実装コメントに明記）と「共有版」（V 層）が同じ行に並び、似た名前・別意味。
  「スキーマ提案」と「スキーマ管理」も名称酷似・別機能。
- 破壊的操作の確認 UI が重大度と対応しない: 削除は名前入力必須の丁寧なモーダル
  （admin.js:768-864）だが、**不可逆の骨格凍結**・ライブラリ廃止・ステージ上書き再実行は
  素の `confirm()` のみ（admin.js:1994, 2010, 532）。学習者側も同様に不統一
  （チャット削除は confirm あり、enroll は確認なし）。
- コース管理タブが `GET /admin/courses` の返す `is_published` / binding 進捗を**捨てて描画**
  しており、公開状態・地図紐付けを目的の画面で確認できない（admin.py:2089-2153 vs admin.js:5885-5926）。

### G6. ガイダンス機構のカバレッジ不足【重大度: 中】

複雑さを吸収するために作られた 2 機構が、複雑さの増加に追随していない。

- Admin Copilot: capability **15 件**のみ。C/D/R/W/L/V 層・スキーマ提案は未登録で、
  `KNOWN_SCREENS` に `knowledge-library` すら無く**構造的に案内不能**（capabilities.py:24-37）。
- G 層 next-steps: ルール **6 件**のみ。C/D/R/W/L/V 層の滞留作業は「次にやること」に現れない。
- しかも両者とも壊れた公開導線を案内し続ける（G1-6）。ガイダンスの単一の真実源（capability
  registry）が実 UI と乖離しており、「registry に登録された操作のみ案内する」という P1 の
  安全設計が、逆に「実在しない操作を案内する」形で破れている。

### G7. ビジョン自体の未完部分（意図的先送りと文書間の緊張）【重大度: 記録】

実装バグではなくビジョン側の構造的な未完・緊張。ロードマップ判断の材料として記録する。

- **E 層（段階的翻訳）が未実装**: 「パイプライン生成物は専門家にしか読めない」という問題認識に
  対する回答が存在せず、「入門者が興味を持って手に取れる」という約束は未達。
- **旅（journey）はコース内 sources 限定**（コース横断は cross_course_hint の一行のみ）。
  ビジョンの「関心が芽生えるネットワークをたどる旅」は部分実装。旅カードの終点は frontier_note
  の行き止まりで次の行動導線が無い（personal-map.js:637-731）。
- **Phase B は片肺**: 学習者側の重ね合わせは手厚いが、教員側集約は API のみ（G2 参照）。
  「どこで繋がりを見失うか」側の集約は v1 で意図的に見送り。
- **R 層のみ「教員確定なしで自動配信」の例外設計**（status='auto'）で、他層が徹底する
  「候補は人間確定まで非表示」との一貫性に緊張が残る（設計書内で意識されているが未解消）。
- 「全体は一つに見える」vs「神の視点を作らない」（KN-1）: 疎な同一性リンクによる孤立化リスクは
  本質的に未解決——そして肝心の identity-links UI が未接続（G2）のため、リンク層は現状
  ほぼ空のまま。
- 既存レビュー（2026-07-15、personal_knowledge_network_review.md /
  element_deliberation_workspace_review.md）の P1/P2 指摘（journey の閲覧可否・retired entry
  経由 traversal・equation リンクの document_id 衝突・shared_part 権限）は一部対応済みの記述が
  あるが、実装再検証は本調査の範囲外。

## 4. 全体考察 — ギャップの共通パターン

1. **「層を積む」開発モデルの負債が UI に集中している。** バックエンドは層ごとに完結度が高く
   ガードレールも堅牢だが、フロントは層ごとに導線を「間借り」して増築されており、
   (a) 接続されないまま残る層（U/W-Phase1/Phase B）、(b) 埋もれる層（B 層 digest、R 層
   キュー）、(c) 巡回先が増え続ける層（C/D/L/V）に分化した。**次の層を積む前に、層を横断する
   UI の背骨（対象中心のワークベンチ、滞留作業の集約）を検討すべき段階**にある。
2. **安全側原則（fail-closed・非通知・candidate 非表示）の「代償の設計」が抜けている。**
   原則自体はビジョン通りだが、「消える」ことを選んだ以上、(a) 空状態の説明文、(b) 障害と
   空の区別、(c) 準備中表示、が対になっていないと、ユーザーには壊れたシステムと区別が
   つかない。
3. **人間確定主義の UI が非対称。** 「AI は候補のみ・確定は人間」を徹底した結果、確定操作の
   UI が層の数だけ必要になるが、D 層 verification_status・W 層 identity-links のように
   **確定手段そのものが未提供**の箇所では、原則が「誰も確定できない」状態として現れている。
4. **ガイダンス機構は作った時点のスナップショット。** capability registry / next-steps ルールは
   増築に自動追随しないため、実 UI との乖離（存在しない公開ボタンへの案内）が既に発生している。
   registry と実 UI の整合を守るガードレールが無い。

## 5. 次に議論すべき論点（修正着手前の意思決定事項）

1. **公開モデルの確定**: publish 撤去後の正式な公開手段は「visibility=public」か「グループ共有
   のみ」か。決定に応じて G 層ルール・Copilot capability・操作 KB を一括更新する必要がある。
2. **G1-2（initApp 回帰）の即時修正**は判断不要レベルだが、修正時に「学生のグループ参加 UX」
   全体（招待コード入力の導線位置）を見直すか、最小修正に留めるか。
3. **空状態の統一ポリシー**: fail-closed 非表示を維持する箇所と、「準備中/対象なし」の説明を
   出す箇所の線引き（不変条項に抵触しない範囲の設計指針が要る）。
4. **横断インボックス構想**: V 層🔔を C/D/R/L 層の滞留作業に拡張するか（状態通知基盤は既に
   `user_notifications` に統合済みで受け皿はある）。
5. **E 層着手の優先度**: 「入門者への約束」をいつ果たすか。W 層 Phase1/2（identity-links UI）
   との先後関係。
